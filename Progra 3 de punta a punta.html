Unidad 1

Complejidad temporal

La complejidad no mide cuántos segundos tarda un programa. Mide cómo crece la cantidad de operaciones cuando crece el tamaño de la entrada n. Responde a la pregunta: ¿cómo escala el algoritmo cuando el problema se hace más grande?

Los segundos dependen de la compu, del lenguaje y de lo que esté corriendo al mismo tiempo. Contar operaciones no depende de nada de eso: si un algoritmo hace n2 operaciones, al duplicar la entrada va a hacer cuatro veces más trabajo en cualquier máquina.

T(n): el costo como función

T(n) es la cantidad de operaciones elementales que hace el algoritmo cuando recibe una entrada de tamaño n. Una operación elemental es cualquier cosa que tarda tiempo constante: una suma, una comparación, una asignación, acceder a v[i].

Ejemplo: sumar los elementos de un arreglo.

Suma.java
int suma(int[] v) {
    int total = 0;                      // 1 operación
    for (int i = 0; i < v.length; i++) {  // n vueltas
        total += v[i];                  // 1 operación por vuelta
    }
    return total;                       // 1 operación
}

Contando a grandes rasgos: T(n) = n + 2. Lo que importa es el término que domina cuando n es grande, así que decimos que es O(n).

Mejor caso, peor caso y caso promedio

Para el mismo n, el algoritmo puede tardar distinto según cómo venga la entrada. Con la búsqueda lineal (recorrer el arreglo hasta encontrar x):

  • Mejor caso: x está en la primera posición. Hace 1 comparación.
  • Peor caso: x está última o no está. Hace n comparaciones.
  • Caso promedio: si puede estar en cualquier lugar con igual probabilidad, hace n/2 en promedio, que sigue siendo lineal.

Cuando en un parcial te preguntan "¿qué complejidad tiene?" sin aclarar nada, casi siempre esperan el peor caso, porque es la garantía: nunca va a tardar más que eso.

Ajuste a tus notas

En tus apuntes quedó "Big O = peor caso" y "Omega = mejor caso". En la práctica se usa así y no está mal para el parcial, pero conceptualmente son dos cosas distintas: los casos (mejor/peor/promedio) dicen qué entrada miramos, y las notaciones (O/Ω/Θ) dicen qué tipo de cota damos sobre esa entrada.

Por ejemplo, el peor caso de la búsqueda lineal es Θ(n) (cota ajustada) y el mejor caso es Θ(1). Si tenés que decirlo en una sola frase: "la búsqueda lineal es O(n)" porque en ningún caso supera lo lineal.

Ejemplo de la definición

¿Es f(n) = 3n2 + 5n + 2 de orden O(n2)? Hay que encontrar c y n0. Probamos con c = 4: necesitamos 3n2 + 5n + 2 ≤ 4n2, o sea n2 − 5n − 2 ≥ 0, que vale desde n = 6 (36 − 30 − 2 = 4 ≥ 0). Entonces con c = 4 y n0 = 6 se cumple. Sí, es O(n²)

De acá salen las dos reglas que usás siempre: las constantes no importan (3n2 es O(n2)) y se queda el término que más crece (5n + 2 desaparece).

Cómo calcular la complejidad de un código

  1. Operaciones simples (+, -, asignaciones, comparaciones, acceso a arreglo): O(1).
  2. Un for que recorre n elementos: O(n), multiplicado por lo que cueste el cuerpo.
  3. Bucles anidados: se multiplican. Dos for de n: O(n2). Tres: O(n3).
  4. Bloques uno después del otro: se suman, y queda el mayor. Un for de n seguido de otro de n: O(n + n) = O(n).
  5. Bucles que multiplican o dividen la variable (i *= 2, i /= 2): O(log n).
  6. Funciones recursivas: se plantea la recurrencia T(n) y se resuelve (Unidad 2).

Un bucle simple

Java
for (int i = 0; i < n; i++) {
    System.out.println(i);
}

El cuerpo se ejecuta n veces: O(n)

Dos bucles anidados

Java
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        System.out.println(i + " " + j);
    }
}

Por cada una de las n vueltas de afuera, el de adentro da n vueltas: n · n. O(n²)

Bucle "triangular" (el de adentro depende del de afuera)

Java
for (int i = 0; i < n; i++) {
    for (int j = 0; j < i; j++) {
        System.out.println(i + " " + j);
    }
}

Acá el de adentro no da siempre n vueltas: da 0, después 1, después 2… hasta n − 1. Total: 0 + 1 + 2 + … + (n − 1) = n(n − 1)/2. Es la mitad del caso anterior, pero las constantes no importan. O(n²)

Bucle que duplica

Java
for (int i = 1; i < n; i *= 2) {
    System.out.println(i);
}

i toma los valores 1, 2, 4, 8, …, 2k. Corta cuando 2k ≥ n, o sea cuando k = log2 n. O(log n)

Regla mental

Siempre que veas i *= 2 o i /= 2 (o n /= 3, o "parto el problema a la mitad"), pensá inmediatamente en logaritmos, no necesariamente en búsqueda binaria. La base del logaritmo no importa en la notación O porque log3 n = log2 n / log2 3, que es una constante por log2 n.

Sumas que aparecen todo el tiempo

Muchos análisis terminan en una suma. Cuando veas una, preguntate de qué tipo es:

Suma aritmética

Sn = n(a1 + an) / 2cantidad de términos × (primero + último) / 2

Para 1 + 2 + … + n: hay n términos, el primero es 1 y el último n, entonces da n(1 + n)/2. El truco de Gauss: si sumás la lista al derecho y al revés, cada par da n + 1, hay n pares y contaste todo dos veces.

Suma geométrica

∑k=0∞ a rk = a / (1 − r),   |r| < 1cada término es el anterior multiplicado por r

Sirve para las sumas que se achican: n + n/2 + n/4 + … es a = n y r = 1/2, así que da como mucho n / (1 − 1/2) = 2n. Para las que crecen (1 + 2 + 4 + … + 2k) se usa la versión finita: da 2k+1 − 1, o sea menos del doble del último término. En los dos casos la conclusión es la misma: en una suma geométrica manda el término más grande.

Unidad 2

Recurrencias y Teorema Maestro

Cuando una función es recursiva no podés contar vueltas de un for: el costo depende de sí mismo. Lo que se hace es escribir una recurrencia, una ecuación que dice cuánto cuesta T(n) en función de lo que cuestan las llamadas más chicas.

Cómo se arma la recurrencia a partir del código

Mirás tres cosas:

  1. Cuántas llamadas recursivas hace cada ejecución (eso es a).
  2. De qué tamaño es cada llamada: ¿la mitad (n/2)? ¿uno menos (n − 1)?
  3. Cuánto trabajo hace fuera de las llamadas (dividir, combinar, un for…). Eso es f(n).

Búsqueda binaria recursiva

Java
boolean buscar(int[] v, int x, int ini, int fin) {
    if (ini > fin) return false;
    int medio = (ini + fin) / 2;
    if (v[medio] == x) return true;
    if (v[medio] > x) return buscar(v, x, ini, medio - 1);
    return buscar(v, x, medio + 1, fin);
}

1 llamada, de tamaño mitad, trabajo extra constante:
T(n) = T(n/2) + 1

MergeSort

Java
void mergeSort(int[] v, int ini, int fin) {
    if (ini >= fin) return;
    int medio = (ini + fin) / 2;
    mergeSort(v, ini, medio);
    mergeSort(v, medio + 1, fin);
    merge(v, ini, medio, fin); // O(n)
}

2 llamadas, cada una de la mitad, y el merge recorre todo:
T(n) = 2T(n/2) + n

Método 1: desenrollar

Reemplazás T por su definición una y otra vez hasta ver el patrón. Es el método que sirve cuando el problema se achica restando (n − 1), donde el Teorema Maestro no aplica.

Ejemplo: T(n) = T(n − 1) + n (QuickSort en el peor caso)

T(n) = T(n-1) + n
     = T(n-2) + (n-1) + n
     = T(n-3) + (n-2) + (n-1) + n
     = ...
     = T(1) + 2 + 3 + ... + (n-1) + n
     ≈ 1 + 2 + ... + n = n(n+1)/2      →  O(n²)

Ejemplo: T(n) = 2T(n − 1) + 1 (Torres de Hanoi)

T(n) = 2T(n-1) + 1
     = 2[2T(n-2) + 1] + 1         = 4T(n-2) + 2 + 1
     = 4[2T(n-3) + 1] + 2 + 1     = 8T(n-3) + 4 + 2 + 1
     = ...
     = 2^k T(n-k) + (2^(k-1) + ... + 2 + 1)
con k = n-1:  2^(n-1)·T(1) + 2^(n-1) - 1     →  O(2ⁿ)

Dos llamadas que solo restan 1 duplican el trabajo en cada nivel: eso es exponencial. Es exactamente lo que le pasa a Fibonacci recursivo (Unidad 7).

Método 2: árbol de recursión

Dibujás las llamadas como un árbol, anotás cuánto trabajo extra hace cada nodo, y sumás por niveles. Para T(n) = 2T(n/2) + n:

nivel 0:              n                         →  n
nivel 1:        n/2       n/2                   →  n
nivel 2:     n/4  n/4  n/4  n/4                 →  n
  ...                    ...                       ...
nivel log n:  1  1  1  1  ...  1  (n hojas)     →  n
─────────────────────────────────────────────────────────
log n niveles × n por nivel                     =  n log n

Cada nivel cuesta lo mismo (n) y hay log n niveles porque dividimos por 2 hasta llegar a 1. O(n log n)

Método 3: Teorema Maestro

Es una receta para resolver de una las recurrencias de la forma:

T(n) = a · T(n/b) + f(n)a ≥ 1: cantidad de llamadas recursivas · b > 1: en cuánto se divide el tamaño · f(n): trabajo fuera de las llamadas

La idea es comparar dos cosas: el trabajo de la raíz, f(n), contra el trabajo de las hojas, que es nlogb a (el árbol tiene logb n niveles y alogb n = nlogb a hojas). El que pesa más, gana.

CasoCondiciónResultadoIntuición
1f(n) crece más lento que nlogb aΘ(nlogb a)Ganan las hojas: hay tantas llamadas que el trabajo de abajo domina.
2f(n) crece igual que nlogb aΘ(f(n) · log n)Empate: cada nivel cuesta lo mismo y hay log n niveles.
3f(n) crece más rápido que nlogb aΘ(f(n))Gana la raíz: el trabajo de arriba domina.
Versión rápida (la que vas a usar el 95% de las veces)

Si f(n) = nd, compará el exponente d con logb a:

  • d < logb a → Θ(nlogb a)
  • d = logb a → Θ(nd log n)
  • d > logb a → Θ(nd)

Recordá: una constante es n0 (o sea d = 0) y n es n1.

Resolución completa paso a paso: T(n) = 8T(n/2) + n2

  1. Identifico: a = 8, b = 2, f(n) = n2 (o sea d = 2).
  2. Calculo log2 8 = 3 (porque 23 = 8). Las hojas pesan n3.
  3. Comparo: d = 2 < 3. La raíz crece más lento que las hojas: caso 1.
  4. Resultado: Θ(n³)

Karatsuba: T(n) = 3T(n/2) + n

a = 3, b = 2, d = 1. log2 3 ≈ 1,585. Como 1 < 1,585 es caso 1: Θ(n^1,585). Es mejor que la multiplicación de la escuela, que es n2 (ver Karatsuba).

Cuándo NO se puede usar
  • Cuando el problema se achica restando: T(n − 1), T(n − 2). Ahí desenrollás.
  • Cuando las llamadas son de tamaños distintos: T(n/3) + T(2n/3) + n. Ahí va árbol de recursión.
  • En el caso 3, además hay que chequear la condición de regularidad: a·f(n/b) ≤ c·f(n) con c < 1. Con polinomios (nd) siempre se cumple, así que en la práctica no te preocupa.

Unidad 3

Divide y Conquista

"Divido el problema, resuelvo las partes y combino las soluciones." Partís el problema en subproblemas más chicos e independientes del mismo tipo, los resolvés recursivamente y juntás los resultados.

El esquema

  1. Caso base: si el problema es lo bastante chico (un elemento, rango vacío), se resuelve directo.
  2. Dividir: partir en subproblemas más chicos (generalmente mitades).
  3. Conquistar: resolver cada subproblema con una llamada recursiva.
  4. Combinar: armar la solución del problema original con las soluciones de las partes.
Esquema general
Solucion resolver(Problema p) {
    if (esChico(p)) {
        return resolverDirecto(p);       // caso base
    }
    List<Problema> partes = dividir(p);  // dividir
    List<Solucion> sols = new ArrayList<>();
    for (Problema parte : partes) {
        sols.add(resolver(parte));       // conquistar
    }
    return combinar(sols);               // combinar
}

La complejidad sale casi siempre con el Teorema Maestro: a es la cantidad de partes, b en cuánto se achican, f(n) lo que cuesta dividir más combinar.

La diferencia con Programación Dinámica

En D&C los subproblemas son independientes: la mitad izquierda de MergeSort no tiene nada que ver con la derecha. Si los subproblemas se repiten (como en Fibonacci), D&C recalcula lo mismo muchas veces y conviene PD.

Búsqueda binaria

Precondición: el arreglo tiene que estar ordenado. Comparás x con el elemento del medio. Si es igual, encontraste. Si el del medio es más grande, x solo puede estar a la izquierda (todo lo de la derecha es todavía más grande), así que descartás la mitad derecha. Si es más chico, descartás la izquierda. En cada paso tirás la mitad de lo que queda.

BusquedaVector.java
public class BusquedaVector {

    public static boolean pertenece(int[] vector, int x) {
        int inicio = 0;
        int fin = vector.length - 1;

        while (inicio <= fin) {
            int medio = inicio + (fin - inicio) / 2;

            if (vector[medio] == x) {
                return true;
            } else if (vector[medio] > x) {
                fin = medio - 1;      // busca en la mitad izquierda
            } else {
                inicio = medio + 1;   // busca en la mitad derecha
            }
        }
        return false;                 // no se encontró
    }
}

¿Por qué inicio + (fin - inicio) / 2 y no (inicio + fin) / 2? Dan lo mismo, pero si inicio y fin son enormes la suma puede pasarse del máximo de un int (overflow). La primera forma nunca se pasa.

Complejidad: T(n) = T(n/2) + 1 → O(log n). Con un millón de elementos son como mucho 20 comparaciones.

MergeSort

Divide fácil, combina con trabajo. Partís el arreglo por la mitad sin mirar los valores, ordenás cada mitad recursivamente y después las intercalás (merge): como las dos mitades ya están ordenadas, vas comparando la primera de cada una y sacás la menor.

MergeSort.java
public static void mergeSort(int[] v, int inicio, int fin) {
    // CASO BASE
    if (inicio >= fin) {
        return;
    }
    int medio = (inicio + fin) / 2;

    // DIVIDIR
    mergeSort(v, inicio, medio);
    mergeSort(v, medio + 1, fin);

    // COMBINAR
    merge(v, inicio, medio, fin);
}

public static void merge(int[] v, int inicio, int medio, int fin) {
    int[] auxiliar = new int[fin - inicio + 1];
    int i = inicio;       // recorre la mitad izquierda
    int j = medio + 1;    // recorre la mitad derecha
    int k = 0;            // posición en auxiliar

    while (i <= medio && j <= fin) {
        if (v[i] <= v[j]) {
            auxiliar[k] = v[i];
            i++;
        } else {
            auxiliar[k] = v[j];
            j++;
        }
        k++;
    }
    // Copiar sobrantes de la izquierda
    while (i <= medio) {
        auxiliar[k] = v[i];
        i++;
        k++;
    }
    // Copiar sobrantes de la derecha
    while (j <= fin) {
        auxiliar[k] = v[j];
        j++;
        k++;
    }
    // Copiar resultado al arreglo original
    for (i = inicio, k = 0; i <= fin; i++, k++) {
        v[i] = auxiliar[k];
    }
}

QuickSort

Particiona con trabajo, casi no combina. Elegís un pivote y reacomodás el arreglo para que todo lo menor o igual quede a su izquierda y todo lo mayor a su derecha. El pivote ya queda en su posición final. Después ordenás recursivamente cada lado. No hace falta combinar nada: cuando los dos lados están ordenados, todo está ordenado.

QuickSort.java
public class QuickSort {

    public static void quickSort(int[] v, int inicio, int fin) {
        if (inicio < fin) {
            int pivote = partition(v, inicio, fin);
            quickSort(v, inicio, pivote - 1);
            quickSort(v, pivote + 1, fin);
        }
    }

    // Lomuto: el pivote es el último elemento
    public static int partition(int[] v, int inicio, int fin) {
        int pivote = v[fin];
        int i = inicio - 1;   // último índice de la zona "<= pivote"

        for (int j = inicio; j < fin; j++) {
            if (v[j] <= pivote) {
                i++;
                int aux = v[i];
                v[i] = v[j];
                v[j] = aux;
            }
        }
        // el pivote va justo después de la zona de menores
        int aux = v[i + 1];
        v[i + 1] = v[fin];
        v[fin] = aux;

        return i + 1;
    }
}

Cómo funciona el partition de Lomuto

Pensalo con dos punteros. j recorre el arreglo de izquierda a derecha mirando cada elemento. i marca dónde termina la zona de los "chicos" (los ≤ pivote). Arranca en inicio − 1 porque al principio esa zona está vacía. Cada vez que j encuentra un chico, agranda la zona (i++) y lo mete adentro con un swap. Al final, el pivote se cambia con v[i + 1], que es el primer "grande".

Complejidad y el problema del pivote

  • Mejor caso / promedio: el pivote cae más o menos en el medio y parte en dos mitades parecidas (50-50, o incluso 30-70). T(n) = 2T(n/2) + n → O(n log n).
  • Peor caso: el pivote es siempre el mínimo o el máximo del subarreglo. Un lado queda vacío y el otro con n − 1 elementos. T(n) = T(n − 1) + n → n + (n − 1) + (n − 2) + … = n(n − 1)/2 → O(n2).

Con Lomuto (último elemento como pivote), el peor caso aparece con un arreglo ya ordenado (el último es siempre el máximo) o ordenado al revés (es siempre el mínimo). Paradójicamente, lo "más fácil" es lo que peor le sale.

Karatsuba (multiplicación rápida)

Multiplicar dos números de n dígitos "como en la escuela" cuesta O(n2): cada dígito de uno por cada dígito del otro. Karatsuba lo baja usando D&C y un truco algebraico.

Partís cada número en dos mitades de m dígitos:

x = a · 10m + b     y = c · 10m + d
x · y = ac · 102m + (ad + bc) · 10m + bd

Así como está, hacen falta 4 multiplicaciones de la mitad de tamaño (ac, ad, bc, bd), y 4T(n/2) + n sigue siendo n2. El truco: el término del medio se saca con una sola multiplicación más.

(a + b)(c + d) − ac − bd = ad + bcac y bd ya los tenías calculados

Son 3 multiplicaciones en vez de 4. Las sumas y los corrimientos (multiplicar por potencias de 10) son lineales. Recurrencia: T(n) = 3T(n/2) + n → O(n^log₂3) ≈ O(n^1,585)

Karatsuba.java
public static long karatsuba(long x, long y) {
    if (x < 10 || y < 10) {
        return x * y;                      // caso base: un dígito
    }
    int n = Math.max(Long.toString(x).length(), Long.toString(y).length());
    int m = n / 2;
    long p = (long) Math.pow(10, m);

    long a = x / p, b = x % p;             // x = a·10^m + b
    long c = y / p, d = y % p;             // y = c·10^m + d

    long ac = karatsuba(a, c);
    long bd = karatsuba(b, d);
    long medio = karatsuba(a + b, c + d) - ac - bd;   // ad + bc

    return ac * p * p + medio * p + bd;
}

3.9

Explicá con tus palabras por qué una mala elección del pivote hace que QuickSort pase de O(n log n) a O(n2).

Ver resolución

El partition siempre cuesta lineal en el tamaño del subarreglo. Lo que cambia es cuántos niveles de recursión hay. Si el pivote parte más o menos al medio, el tamaño se divide en cada nivel y hay log n niveles, cada uno con trabajo total n: n log n. Si el pivote es siempre un extremo, cada nivel solo saca un elemento (el pivote), quedan particiones de tamaño 0 y n − 1, y hay n niveles: n + (n − 1) + … + 1 = n(n − 1)/2, cuadrático.

Unidad 4

Greedy (algoritmos voraces)

En cada paso elegís la opción que parece mejor en ese momento, la tomás de forma definitiva y no volvés atrás. No te preocupás por las decisiones futuras.

Greedy responde a la pregunta "¿cuál es la mejor opción que puedo tomar ahora?", mientras que el problema en realidad pregunta "¿cuál es la mejor solución considerando todo el problema?". A veces las dos preguntas tienen la misma respuesta y Greedy es perfecto (y muy rápido). Otras veces no, y Greedy da una solución que funciona pero no es la óptima.

Cómo trabaja

  1. Tenemos un problema.
  2. Elegimos la mejor opción disponible según un criterio (la moneda más grande, la actividad que termina antes, el objeto con mejor valor/peso…).
  3. Tomamos esa decisión definitivamente: no se deshace nunca.
  4. Reducimos el problema (lo que queda por resolver).
  5. Volvemos a elegir la mejor opción con el mismo criterio.
  6. Repetimos hasta construir la solución.
Esquema general
Solucion greedy(List<Candidato> candidatos) {
    Solucion sol = new Solucion();
    ordenarSegunCriterio(candidatos);     // casi siempre hay un sort
    for (Candidato c : candidatos) {
        if (esFactible(sol, c)) {        // ¿lo puedo agregar sin romper nada?
            sol.agregar(c);               // decisión definitiva
        }
    }
    return sol;
}

Como casi siempre se ordena al principio, la complejidad típica de un Greedy es O(n log n): el sort domina y después hay una sola pasada lineal.

Las dos propiedades que tiene que cumplir

Propiedad de elección greedy

Podés tomar la decisión localmente óptima sin perder la posibilidad de llegar a una solución óptima global. O sea: existe alguna solución óptima que incluye tu primera elección.

Subestructura óptima

Después de elegir, el problema que queda también tiene una solución óptima, y esa solución, combinada con tu elección, da el óptimo del problema completo.

Cómo se justifica en un parcial

Para decir que Greedy NO funciona alcanza con un contraejemplo: una entrada concreta donde Greedy da peor que el óptimo.

Para decir que SÍ funciona se usa el argumento de intercambio: tomás cualquier solución óptima, mostrás que podés cambiar uno de sus elementos por la elección greedy sin empeorarla, y concluís que hay un óptimo que empieza con la elección greedy.

Cambio de monedas

Problema: dar un monto usando la menor cantidad de monedas. Criterio greedy: usar siempre la moneda más grande que entre.

CambioMonedas.java
// monedas ordenadas de mayor a menor
public static int cambioMonedas(int[] monedas, int monto) {
    int cantidad = 0;
    for (int moneda : monedas) {
        while (monto >= moneda) {
            monto -= moneda;
            cantidad++;
        }
    }
    return cantidad;
}

Con monedas {25, 10, 5, 1} y monto 63: 25 + 25 + 10 + 1 + 1 + 1 = 6 monedas, que es el óptimo. Con los sistemas de monedas "normales" (llamados canónicos) Greedy siempre da el óptimo.

Pero con monedas {4, 3, 1} y monto 6:

  • Greedy: agarra el 4 (es la más grande que entra), quedan 2, agarra 1 + 1. Total: 3 monedas (4 + 1 + 1).
  • Óptimo: 3 + 3. Total: 2 monedas.

Haber tomado el 4 fue una buena decisión "ahora", pero arruinó el futuro. No se cumple la propiedad de elección greedy. Para este caso hay que usar Programación Dinámica.

Selección de actividades

Problema: tenés actividades con hora de inicio y de fin, y un solo recurso (un aula, una sala). Querés hacer la mayor cantidad de actividades sin que se superpongan.

Criterio greedy correcto: elegir siempre la que termina antes entre las compatibles con lo ya elegido. La intuición: cuanto antes se libere el recurso, más lugar queda para las demás.

SeleccionActividades.java
import java.util.*;

public static List<Actividad> seleccionar(List<Actividad> actividades) {
    actividades.sort(Comparator.comparingInt(a -> a.fin));

    List<Actividad> resultado = new ArrayList<>();
    Actividad ultima = actividades.get(0);
    resultado.add(ultima);

    for (int i = 1; i < actividades.size(); i++) {
        Actividad actual = actividades.get(i);
        if (actual.inicio >= ultima.fin) {   // no se superpone
            resultado.add(actual);
            ultima = actual;
        }
    }
    return resultado;
}

Complejidad: sort O(n log n) + una pasada O(n) = O(n log n).

Criterios que parecen buenos y fallan
  • La que dura menos: con (1, 5), (4, 7), (6, 10), la más corta es (4, 7), pero choca con las otras dos. Greedy hace 1 actividad, el óptimo hace 2: (1, 5) y (6, 10).
  • La que empieza antes: con (0, 10), (1, 2), (3, 4), elige (0, 10) que bloquea todo. Greedy hace 1, el óptimo hace 2.

Ojo con decir "la que tarda menos": el criterio es la que termina antes.

Por qué funciona (argumento de intercambio): sea g la actividad que termina primero. Tomá cualquier solución óptima y su primera actividad o. Como g termina antes o igual que o, si reemplazás o por g no chocás con nada nuevo y la cantidad es la misma. Entonces hay un óptimo que empieza con g, y lo que queda es el mismo problema más chico.

Mochila fraccionaria

Problema: una mochila con capacidad W y objetos con peso y valor. Querés maximizar el valor. Acá se puede llevar una fracción de un objeto (pensá en arena, harina, oro en polvo).

Criterio greedy: ordenar por valor/peso de mayor a menor y meter enteros los que entren. Cuando uno no entra completo, se lleva la fracción que llena la mochila y se termina.

MochilaFraccionaria.java
public static double mochilaFraccionaria(List<Objeto> objetos, int capacidad) {
    // mayor valor/peso primero
    objetos.sort((a, b) -> Double.compare(
            (double) b.valor / b.peso,
            (double) a.valor / a.peso));

    double valorTotal = 0;
    int capacidadRestante = capacidad;

    for (Objeto objeto : objetos) {
        if (objeto.peso <= capacidadRestante) {
            capacidadRestante -= objeto.peso;
            valorTotal += objeto.valor;
        } else {
            double fraccion = (double) capacidadRestante / objeto.peso;
            valorTotal += objeto.valor * fraccion;
            break;
        }
    }
    return valorTotal;
}

Es seguro elegir primero el de mejor valor/peso porque cada kilo de mochila rinde lo máximo posible, y como podés fraccionar nunca te queda espacio desperdiciado.

Unidad 5

Grafos y Árbol de Expansión Mínima

Un grafo es un conjunto de vértices (nodos) unidos por aristas. Si las aristas tienen un número (costo, distancia, tiempo), es un grafo ponderado. Kruskal y Prim encuentran la forma más barata de conectar todos los vértices.

Lo mínimo de grafos que necesitás

  • V = cantidad de vértices, E = cantidad de aristas (de edges).
  • No dirigido: la arista A–B se puede recorrer para los dos lados. Dirigido: A→B solo de A a B.
  • Conexo: desde cualquier vértice se puede llegar a cualquier otro.
  • Ciclo: un camino que vuelve al vértice de donde salió.
  • Árbol: un grafo conexo y sin ciclos. Un árbol con V vértices tiene exactamente V − 1 aristas.

En código, la forma más usada es la lista de adyacencia: para cada vértice, la lista de aristas que salen de él. Los vértices se numeran 0, 1, 2… (A = 0, B = 1, etc.).

Grafo.java
class Arista {
    int origen, destino, peso;
    Arista(int origen, int destino, int peso) {
        this.origen = origen;
        this.destino = destino;
        this.peso = peso;
    }
}

// grafo.get(u) = aristas que salen de u
List<List<Arista>> grafo = new ArrayList<>();
for (int i = 0; i < n; i++) {
    grafo.add(new ArrayList<>());
}
// arista no dirigida u–v: se agrega en los dos sentidos
grafo.get(u).add(new Arista(u, v, peso));
grafo.get(v).add(new Arista(v, u, peso));

Árbol de expansión mínima (MST)

Dado un grafo conexo, no dirigido y ponderado, un árbol de expansión es un subconjunto de aristas que conecta todos los vértices sin formar ciclos (o sea, V − 1 aristas). El mínimo (MST, Minimum Spanning Tree, también "árbol de recubrimiento mínimo") es el que tiene la menor suma de pesos.

Ejemplo típico: conectar ciudades con fibra óptica gastando lo menos posible. No importa por dónde pase cada conexión, solo que todas queden conectadas y que el total sea mínimo.

Los dos algoritmos son Greedy y los dos dan un MST correcto. Cambia la forma de pensar:

Kruskal

"Voy agarrando las aristas más baratas de todo el grafo, siempre que no formen un ciclo."

¿Cuál es la arista más barata de todo el grafo que todavía puedo usar?

Prim

"Arranco desde un vértice y voy agregando la arista más barata que conecte mi árbol con un vértice que todavía no está."

Desde mi árbol actual, ¿cuál es la arista más barata para crecer?

Kruskal

  1. Ordenar todas las aristas de menor a mayor peso.
  2. Recorrerlas en ese orden. Para cada una: si une dos vértices que todavía no están conectados, se agrega. Si ya estaban conectados (por otro camino), agregarla formaría un ciclo y se descarta.
  3. Cortar cuando se tienen V − 1 aristas.

El problema es saber rápido si dos vértices "ya están conectados". Para eso se usa Union-Find.

Union-Find (conjuntos disjuntos)

Mantiene grupos de vértices conectados. Cada grupo tiene un representante (la raíz). padre[x] dice quién es el padre de x en su grupo; la raíz es su propio padre.

  • find(x): sube de padre en padre hasta la raíz. Dos vértices están en el mismo grupo si tienen la misma raíz.
  • union(a, b): une los dos grupos haciendo que la raíz de uno apunte a la raíz del otro.
UnionFind.java
class UnionFind {
    int[] padre;

    public UnionFind(int n) {
        padre = new int[n];
        for (int i = 0; i < n; i++) {
            padre[i] = i;          // cada uno es su propio grupo
        }
    }

    public int find(int x) {
        if (padre[x] != x) {
            padre[x] = find(padre[x]);   // compresión de camino
        }
        return padre[x];
    }

    public void union(int a, int b) {
        int raizA = find(a);
        int raizB = find(b);
        padre[raizA] = raizB;
    }
}

La línea padre[x] = find(padre[x]) es la compresión de camino: mientras busca la raíz, deja a todos los nodos del camino apuntando directo a ella. Así las próximas búsquedas son casi instantáneas.

Kruskal.java
public static List<Arista> kruskal(List<Arista> aristas, int vertices) {
    // 1. Ordenamos por peso
    aristas.sort(Comparator.comparingInt(a -> a.peso));

    List<Arista> resultado = new ArrayList<>();
    UnionFind uf = new UnionFind(vertices);

    // 2. Revisamos las aristas
    for (Arista arista : aristas) {
        int raizOrigen = uf.find(arista.origen);
        int raizDestino = uf.find(arista.destino);

        // Si pertenecen a conjuntos distintos, no forma ciclo
        if (raizOrigen != raizDestino) {
            resultado.add(arista);
            uf.union(arista.origen, arista.destino);
        }

        // Un MST tiene V - 1 aristas
        if (resultado.size() == vertices - 1) {
            break;
        }
    }
    return resultado;
}

Complejidad: ordenar las aristas cuesta O(E log E) y las operaciones de Union-Find son casi constantes. Total: O(E log E) (que es lo mismo que O(E log V)).

Prim

  1. Arrancar desde un vértice cualquiera. Marcarlo como visitado.
  2. Meter en una cola de prioridad todas las aristas que salen de él.
  3. Sacar la arista más barata. Si su destino ya está en el árbol, se ignora (formaría ciclo). Si no, se agrega, se marca el destino y se encolan sus aristas hacia vértices no visitados.
  4. Repetir hasta que la cola quede vacía (o se visiten todos).
Prim.java
public static int prim(List<List<Arista>> grafo, int inicio) {
    int vertices = grafo.size();
    boolean[] visitado = new boolean[vertices];

    PriorityQueue<Arista> cola = new PriorityQueue<>(
            Comparator.comparingInt(a -> a.peso));

    // arista ficticia de costo 0 para entrar al vértice inicial
    cola.add(new Arista(-1, inicio, 0));
    int costoTotal = 0;

    while (!cola.isEmpty()) {
        Arista actual = cola.poll();

        // Si ya está en el árbol, se descarta
        if (visitado[actual.destino]) {
            continue;
        }

        // Lo agregamos
        visitado[actual.destino] = true;
        costoTotal += actual.peso;

        // Agregamos las conexiones hacia vértices nuevos
        for (Arista vecino : grafo.get(actual.destino)) {
            if (!visitado[vecino.destino]) {
                cola.add(vecino);
            }
        }
    }
    return costoTotal;
}

Complejidad: cada arista entra y sale de la cola de prioridad como mucho una vez, y cada operación cuesta O(log E). Total: O(E log V).

Unidad 6

Dijkstra (camino mínimo)

Encuentra el camino más corto desde un vértice origen hasta todos los demás en un grafo con pesos no negativos. El peso representa la distancia o el costo acumulado del camino.

La idea

Mantenés un arreglo dist[] con la mejor distancia conocida hasta cada vértice. Al principio:

  • dist[origen] = 0 (estar parado ahí no cuesta nada).
  • dist[resto] = ∞. ¿Por qué infinito? Porque todavía no sabemos cómo llegar a esos vértices. Cualquier camino que encontremos va a ser mejor que "no tengo camino".

Después repetís:

  1. Elegir el vértice no visitado con menor dist. Esa distancia ya es definitiva: lo marcás como visitado.
  2. Relajar todas sus aristas: fijarte si pasando por él llegás más barato a algún vecino.
  3. Seguir hasta visitar todos (o hasta que la cola quede vacía).

Elegir siempre el más cercano y no volver a tocarlo es una decisión Greedy.

Relajación de una arista

Relajar la arista (u, v) es comprobar si puedo llegar a v más barato pasando por u, que es el vértice que acabo de fijar:

si   dist[u] + peso(u, v) < dist[v]
dist[v] = dist[u] + peso(u, v)    // encontré un camino estrictamente mejor
prev[v] = u                       // y vengo desde u

prev[v] guarda desde qué vértice se llega a v en el mejor camino. Sirve para reconstruir el recorrido al final.

Código

Dijkstra.java
class Nodo {
    int vertice, distancia;
    Nodo(int vertice, int distancia) {
        this.vertice = vertice;
        this.distancia = distancia;
    }
}

public static int[] dijkstra(List<List<Arista>> grafo, int inicio, int[] prev) {
    int n = grafo.size();
    int[] distancia = new int[n];
    boolean[] visitado = new boolean[n];

    Arrays.fill(distancia, Integer.MAX_VALUE);   // "infinito"
    Arrays.fill(prev, -1);
    distancia[inicio] = 0;

    PriorityQueue<Nodo> cola = new PriorityQueue<>(
            Comparator.comparingInt(a -> a.distancia));
    cola.add(new Nodo(inicio, 0));

    while (!cola.isEmpty()) {
        Nodo actual = cola.poll();
        int u = actual.vertice;

        if (visitado[u]) {
            continue;          // entrada vieja de la cola
        }
        visitado[u] = true;    // su distancia ya es definitiva

        for (Arista vecino : grafo.get(u)) {
            int v = vecino.destino;
            int peso = vecino.peso;

            // RELAJACIÓN
            if (distancia[u] != Integer.MAX_VALUE
                    && distancia[u] + peso < distancia[v]) {
                distancia[v] = distancia[u] + peso;
                prev[v] = u;
                cola.add(new Nodo(v, distancia[v]));
            }
        }
    }
    return distancia;
}

Dos detalles del código:

  • El chequeo distancia[u] != Integer.MAX_VALUE evita que MAX_VALUE + peso desborde y dé un número negativo.
  • Un mismo vértice puede entrar varias veces a la cola (cada vez que mejora su distancia). Las entradas viejas se ignoran con el if (visitado[u]) continue.

Reconstruir el camino

Java
List<Integer> camino(int[] prev, int destino) {
    List<Integer> c = new ArrayList<>();
    for (int v = destino; v != -1; v = prev[v]) {
        c.add(0, v);       // se arma de atrás para adelante
    }
    return c;
}

Complejidad: con cola de prioridad, O((V + E) log V).

Dijkstradist[], visitados y relajaciones

Por qué no funciona con pesos negativos

Dijkstra asume que cuando fija un vértice, ningún camino que todavía no exploró puede ser más corto. Eso es cierto solo si los pesos son ≥ 0: cualquier camino nuevo pasa por vértices que ya están más lejos y agregarle aristas solo lo alarga. Con una arista negativa, un camino "largo" puede terminar siendo más corto.

A → B  peso 2
A → C  peso 3
C → B  peso -2

Dijkstra: fija A, relaja B=2, C=3. Fija B (2) como DEFINITIVO.
          Fija C (3), relaja C→B: 3 + (-2) = 1 < 2 ... pero B ya estaba cerrado.
Real:     A→C→B cuesta 1, no 2.

Para pesos negativos se usa Bellman-Ford, que relaja todas las aristas V − 1 veces y cuesta O(V · E). Prim y Kruskal, en cambio, sí funcionan con pesos negativos, porque resuelven otro problema (MST).

Dijkstra vs Prim

Se parecen mucho en el código (los dos usan cola de prioridad y visitado[], los dos son Greedy, los dos arrancan desde un vértice), y por eso se confunden. La diferencia está en qué número se mete en la cola:

Unidad 7

Programación Dinámica

"Voy a analizar distintas posibilidades y reutilizar las soluciones de los subproblemas." Si un problema se parte en subproblemas que se repiten, cada uno se resuelve una sola vez y el resultado se guarda para reusarlo.

Las dos propiedades

Subestructura óptima

La solución óptima del problema se arma a partir de soluciones óptimas de subproblemas más chicos. (Greedy también la necesita.)

Subproblemas superpuestos

Los mismos subproblemas aparecen una y otra vez. Esto es lo que distingue a PD de Divide y Conquista, donde los subproblemas son independientes.

El ejemplo de siempre: Fibonacci

F(n) = F(n − 1) + F(n − 2), con F(0) = 0 y F(1) = 1. La versión recursiva directa:

Fibonacci recursivo
int fibonacci(int n) {
    if (n <= 1) {
        return n;
    }
    return fibonacci(n - 1) + fibonacci(n - 2);
}

Dos formas de hacer PD

Top-down = Memoización

Se empieza por el problema grande, igual que la recursión, pero antes de calcular algo te fijás si ya está guardado. Si está, lo devolvés; si no, lo calculás y lo guardás.

Java
public static int fibonacci(int n, int[] memo) {
    if (n <= 1) {
        return n;
    }
    // ¿ya lo calculé?
    if (memo[n] != -1) {
        return memo[n];
    }
    // lo calculo y lo guardo
    memo[n] = fibonacci(n - 1, memo)
            + fibonacci(n - 2, memo);
    return memo[n];
}
// memo se inicializa con -1:
// Arrays.fill(memo, -1);

Bottom-up = Tabulación

Se empieza por los problemas más chicos y se va llenando una tabla en orden, de forma que cuando necesitás un valor, ya está calculado. Sin recursión.

Java
public static int fibonacci(int n) {
    if (n <= 1) {
        return n;
    }
    int[] dp = new int[n + 1];
    dp[0] = 0;
    dp[1] = 1;

    for (int i = 2; i <= n; i++) {
        dp[i] = dp[i - 1] + dp[i - 2];
    }
    return dp[n];
}

Las dos son O(n): cada fib(i) se calcula una vez. La tabulación se puede optimizar en memoria guardando solo los dos últimos valores (O(1) de espacio), porque dp[i] solo usa dp[i-1] y dp[i-2].

Receta para plantear cualquier PD

  1. Definí el estado: ¿qué significa dp[i] (o dp[i][w])? Escribilo en una oración. Es el paso más importante.
  2. Recurrencia: ¿cómo se calcula dp[i] usando valores más chicos? Pensá en "la última decisión": ¿cuál fue el último paso, el último objeto, la última moneda?
  3. Casos base: los valores que se saben sin calcular.
  4. Orden de llenado: que cada celda dependa solo de celdas ya llenas.
  5. Respuesta: ¿en qué celda queda el resultado?

Escalera (subir de a 1 o de a 2)

Problema: una escalera de n escalones. En cada paso subís 1 o 2. ¿De cuántas formas distintas llegás arriba?

  1. Estado: dp[i] = cantidad de formas de llegar al escalón i.
  2. Recurrencia: al escalón i llegás con un último paso de 1 (desde i−1) o de 2 (desde i−2). Son casos distintos, así que se suman: dp[i] = dp[i-1] + dp[i-2].
  3. Base: dp[0] = 1 (hay una forma de "estar en el piso": no hacer nada) y dp[1] = 1 (un solo paso de 1).
  4. Respuesta: dp[n].
i      0  1  2  3  4  5
dp[i]  1  1  2  3  5  8

Para 5 escalones hay 8 formas. Es Fibonacci corrido un lugar: dp[n] = F(n + 1).

public static int escalera(int n) {
    int[] dp = new int[n + 1];
    dp[0] = 1;
    if (n >= 1) {
        dp[1] = 1;
    }
    for (int i = 2; i <= n; i++) {
        dp[i] = dp[i - 1] + dp[i - 2];

Mochila 0/1

Problema: n objetos con peso y valor, mochila de capacidad W. Cada objeto se lleva entero o no se lleva. Maximizar el valor sin superar la capacidad. (Ya vimos que Greedy no sirve.)

  1. Estado: dp[i][w] = el mejor valor posible usando solo los primeros i objetos con una mochila de capacidad w.
  2. Recurrencia: con el objeto i hay dos opciones.
    • No llevarlo: me quedo con lo mejor que tenía sin él, dp[i-1][w].
    • Llevarlo (si entra, peso_i ≤ w): gano valor_i y me queda w − peso_i de lugar para los objetos anteriores: valor_i + dp[i-1][w - peso_i].
    Me quedo con la mejor.
  3. Base: dp[0][w] = 0 (sin objetos no hay valor) y dp[i][0] = 0 (sin capacidad tampoco).
  4. Respuesta: dp[n][W].
dp[i][w] = max( dp[i−1][w],  valori + dp[i−1][w − pesoi] )la segunda opción solo si pesoi ≤ w
Mochila01.java
public static int mochila(int[] pesos, int[] valores, int capacidad) {
    int n = pesos.length;
    int[][] dp = new int[n + 1][capacidad + 1];   // fila 0 y columna 0 quedan en 0

    for (int i = 1; i <= n; i++) {
        for (int pesoActual = 0; pesoActual <= capacidad; pesoActual++) {
            if (pesos[i - 1] <= pesoActual) {
                dp[i][pesoActual] = Math.max(
                        dp[i - 1][pesoActual],
                        valores[i - 1] + dp[i - 1][pesoActual - pesos[i - 1]]);
            } else {
                dp[i][pesoActual] = dp[i - 1][pesoActual];
            }
        }
    }
    return dp[n][capacidad];
}

Ojo con los índices: la fila i de la tabla corresponde al objeto i − 1 de los arreglos, porque la fila 0 es "sin objetos".

El error más común al hacer la tabla a mano

Cuando el objeto no entra (o no conviene llevarlo), la celda copia la de arriba, no se pone 0. La fila i representa "los primeros i objetos", así que siempre puede hacer lo mismo que la fila anterior. Una fila nunca puede tener un número más chico que la fila de arriba en la misma columna.

Reconstruir qué objetos se llevan: arrancás en dp[n][W] y subís fila por fila. Si dp[i][w] ≠ dp[i-1][w], el objeto i se llevó: lo anotás y restás su peso a w. Si son iguales, no se llevó.

Complejidad: O(n · W) en tiempo y memoria (una celda por par objeto-capacidad).

Cambio de monedas (mínima cantidad) con PD

Es el caso donde Greedy fallaba con {1, 3, 4}.

  1. Estado: dp[m] = mínima cantidad de monedas para pagar exactamente m.
  2. Recurrencia: la última moneda fue alguna c. Antes de ponerla tenía que pagar m − c de la mejor forma: dp[m] = min sobre cada moneda c ≤ m de (dp[m - c] + 1).
  3. Base: dp[0] = 0.
MonedasPD.java
public static int monedasPD(int[] monedas, int monto) {
    int INF = Integer.MAX_VALUE / 2;    // evita overflow al sumar 1
    int[] dp = new int[monto + 1];
    Arrays.fill(dp, INF);
    dp[0] = 0;

    for (int m = 1; m <= monto; m++) {
        for (int c : monedas) {
            if (c <= m && dp[m - c] + 1 < dp[m]) {
                dp[m] = dp[m - c] + 1;
            }
        }
    }
    return dp[monto];   // si quedó INF, no se puede pagar
}

Unidad 8

Backtracking

"Pruebo una posibilidad; si no funciona, vuelvo atrás y pruebo otra." Es una búsqueda sistemática de soluciones: construís la solución de a una decisión por vez y, cuando una decisión no lleva a nada, la deshacés y probás la siguiente.

Elegir → Explorar → Deshacer

            Problema
               │
       ┌───────┴───────┐
       ↓               ↓
    opción A        opción B
       │
    ¿sirve?
     /    \
   sí      no
   ↓        ↓
 avanzar  volver atrás
Tengo muchas posibilidades
          ↓
     exploro una
          ↓
 si no sirve → vuelvo
          ↓
     exploro otra

Las decisiones forman un árbol de estados: la raíz es "no decidí nada", cada nivel es una decisión, y cada hoja es una solución completa (o un callejón sin salida). Backtracking recorre ese árbol en profundidad (DFS). Lo que lo hace "back" es el deshacer: al volver de una rama, el estado queda exactamente como estaba antes de entrar, listo para probar la siguiente opción.

Esquema general
void backtracking(Estado estado) {
    if (esSolucion(estado)) {
        procesarSolucion(estado);
        return;
    }
    for (Opcion opcion : opciones(estado)) {
        if (esValida(estado, opcion)) {     // poda
            // 1. ELEGIR
            elegir(estado, opcion);
            // 2. EXPLORAR
            backtracking(estado);
            // 3. DESHACER
            deshacer(estado, opcion);
        }
    }
}

void permutar(List<Integer> actual, List<Integer> restantes) {

        System.out.println(actual);
        return;

Subconjuntos

Para cada elemento hay dos decisiones: lo incluyo o no lo incluyo. Eso da un árbol binario con 2n hojas.

Subconjuntos.java
void subconjuntos(int[] v, int i, List<Integer> actual) {
    if (i == v.length) {
        System.out.println(actual);
        return;
    }
    // incluyo v[i]
    actual.add(v[i]);
    subconjuntos(v, i + 1, actual);
    actual.remove(actual.size() - 1);    // deshago

    // no incluyo v[i]
    subconjuntos(v, i + 1, actual);
}

Complejidad: O(2ⁿ) subconjuntos. La complejidad de backtracking depende del problema: no es siempre n!. Permutaciones es factorial; subconjuntos es exponencial.

Poda (pruning)

Si en algún momento sabés que una elección ya no puede conducir a una solución válida, no seguís explorando esa rama: "desde acá no hay solución, no sigo". Eso es podar. Es lo que diferencia a Backtracking de la fuerza bruta, que genera todas las combinaciones completas y recién al final se fija cuáles sirven.

Ejemplo: suma de subconjuntos

// v ordenado de menor a mayor

        System.out.println(actual);
        return;

    for (int j = i; j < v.length; j++) {
        if (suma + v[j] > objetivo) {
            break;                       // poda: los siguientes son más grandes
        }
        actual.add(v[j]);
        sumaSubconjuntos(v, j + 1, suma + v[j], objetivo, actual);
        actual.remove(actual.size() - 1);
    }
}

N-Reinas

Colocar n reinas en un tablero de n × n sin que se ataquen (ni misma fila, ni misma columna, ni misma diagonal). Se pone una reina por fila. En cada fila se prueba cada columna; si la casilla está atacada por una reina anterior, se poda.

NReinas.java
// reinas[f] = columna de la reina de la fila f
boolean esSeguro(int[] reinas, int fila, int col) {
    for (int f = 0; f < fila; f++) {
        int c = reinas[f];
        if (c == col || Math.abs(c - col) == fila - f) {
            return false;    // misma columna o misma diagonal
        }
    }
    return true;
}

void nReinas(int[] reinas, int fila) {
    int n = reinas.length;
    if (fila == n) {
        System.out.println(Arrays.toString(reinas));
        return;
    }
    for (int col = 0; col < n; col++) {
        if (esSeguro(reinas, fila, col)) {
            reinas[fila] = col;           // elegir
            nReinas(reinas, fila + 1);    // explorar
            reinas[fila] = -1;            // deshacer
        }
    }
}

Dos reinas están en la misma diagonal si la distancia entre columnas es igual a la distancia entre filas: |c1 − c2| == |f1 − f2|.

Cómo escribir un backtracking desde cero

Si te cuesta pasarlo a código, contestá estas preguntas en orden y cada respuesta es una parte del método:

  1. ¿Qué es una solución parcial? Eso son los parámetros: la lista que voy armando, el índice por el que voy, la suma acumulada…
  2. ¿Cuándo está completa? Ese es el caso base: imprimo/guardo y return.
  3. ¿Qué opciones tengo en este paso? Ese es el for (o las dos llamadas, si es "incluyo / no incluyo").
  4. ¿Cuándo una opción no puede servir? Esa es la poda: un if antes de elegir, o un break.
  5. Elegir, explorar, deshacer: modifico el estado, llamo recursivamente con el paso siguiente, y dejo el estado como estaba.

Recursión común vs Backtracking

Toda solución de backtracking es recursiva, pero no toda recursión es backtracking. Una recursión común (factorial, MergeSort) sigue un único camino de llamadas determinado: no prueba alternativas. Backtracking explora varias alternativas en cada paso, deshace las decisiones al volver para probar otras, y poda las ramas que ya sabe que no sirven.

Escribí un backtracking que imprima todas las formas de elegir k elementos de {1, …, n} sin importar el orden. Probalo con n = 4, k = 2.

void combinaciones(int n, int k, int desde, List<Integer> actual) {
    if (actual.size() == k) {
        System.out.println(actual);
        return;

        combinaciones(n, k, x + 1, actual);   // explorar
        actual.remove(actual.size() - 1);     // deshacer
    }
}

8.6

Explicá la diferencia entre una recursión normal y un backtracking, y entre backtracking y fuerza bruta.

Ver resolución

Recursión vs backtracking: la recursión normal sigue un camino fijo de llamadas (factorial siempre llama con n − 1). Backtracking en cada paso prueba varias opciones, explora cada una, y al volver deshace la decisión para probar la siguiente. Si una rama no sirve, no se equivoca y sigue: vuelve atrás.

Backtracking vs fuerza bruta: la fuerza bruta genera todas las soluciones candidatas completas y después verifica cuáles sirven. Backtracking verifica sobre la marcha y poda: apenas una solución parcial no puede llegar a nada válido, abandona esa rama sin generar todo lo que colgaba de ella.

9.2

Un compañero dice: "PD y Divide y Conquista son lo mismo, los dos parten el problema en subproblemas". ¿Qué le contestás?

Ver resolución

Que los dos parten el problema, pero la diferencia está en los subproblemas. En D&C son independientes (las dos mitades de MergeSort no comparten nada), así que no hay nada que reusar. En PD se superponen: el mismo subproblema aparece muchas veces (como fib(3) dentro de fib(5)), y PD lo calcula una sola vez y lo guarda. Si aplicás D&C a un problema con subproblemas superpuestos, te queda exponencial.

9.3

¿Por qué Greedy suele ser más rápido que PD, y por qué entonces no se usa siempre Greedy?

Ver resolución

Greedy toma una decisión por paso y no la revisa: con un sort y una pasada queda en O(n log n). PD considera todas las opciones de cada subproblema y llena una tabla entera. Pero Greedy solo da el óptimo cuando el problema cumple la propiedad de elección greedy; si no (monedas {1, 3, 4}, mochila 0/1), da una solución factible pero peor. PD siempre da el óptimo porque no descarta ninguna opción sin compararla.

9.4

Dada esta función, escribí su recurrencia, resolvela, y proponé una versión más eficiente con la técnica adecuada.

Java
int caminos(int f, int c) {
    if (f == 0 || c == 0) return 1;
    return caminos(f - 1, c) + caminos(f, c - 1);
}
Ver resolución

Con n = f + c: T(n) = 2T(n − 1) + 1 → O(2n). Es exponencial porque caminos(f-1, c-1) se calcula desde dos lados, y así con todo: subproblemas superpuestos. La solución es PD con tabla de (f + 1) × (c + 1):

Java
int caminos(int f, int c) {
    int[][] dp = new int[f + 1][c + 1];
    for (int i = 0; i <= f; i++) {
        for (int j = 0; j <= c; j++) {
            if (i == 0 || j == 0) {
                dp[i][j] = 1;
            } else {
                dp[i][j] = dp[i - 1][j] + dp[i][j - 1];
            }
        }
    }
    return dp[f][c];
}

O(f · c)

sin negativos → Dijkstra · con negativos → Bellman-Ford

Fórmulas

Teorema Maestro

T(n) = aT(n/b) + nd

  • d < logb a → nlogb a
  • d = logb a → nd log n
  • d > logb a → nd

No aplica con T(n − 1): desenrollar.

Sumas

  • 1 + 2 + … + n = n(n + 1)/2 → n2
  • 1 + 2 + 4 + … + n < 2n → n
  • n + n/2 + n/4 + … < 2n → n
  • i *= 2 o i /= 2 → log n
  • Árbol con V vértices → V − 1 aristas

Trampas típicas

  • Lomuto: en el swap final se cambia v[i+1] con el pivote. Fijate qué número hay realmente en v[i+1] en ese momento.
  • Mochila 0/1 a mano: si no entra, copiá la de arriba. Ninguna celda es menor que la de arriba.
  • Escalera: dp[2] = 2. Para 5 escalones son 8.
  • Dijkstra: dist es acumulada desde el origen, y la relajación pide estrictamente menor.
  • Actividades: la que termina antes, no la que dura menos ni la que empieza antes.
  • Greedy no sirve → mostralo con un contraejemplo concreto.
  • Pesos negativos: Dijkstra no; Bellman-Ford para caminos, Kruskal/Prim siguen andando para MST.
  • Big O es una cota superior: n ∈ O(n2) es verdadero, aunque no ajustado.
