Básico¿Qué es un algoritmo?

Un algoritmo es una secuencia finita de pasos precisos que transforma una entrada en una salida. Una receta de cocina es un algoritmo: entran los ingredientes, sigue pasos concretos ("batir 3 minutos", no "batir un rato") y sale la torta.

En la materia a un algoritmo le pedimos dos cosas:

  • Que sea correcto: para toda entrada válida, da la salida correcta y termina.
  • Que sea eficiente: que no tarde (ni ocupe memoria) de más cuando la entrada crece.
En la vida real

Querés encontrar a "Martínez" en tus contactos. Si la lista está desordenada, la única forma segura es mirar uno por uno: con 1.000 contactos, en el peor caso mirás los 1.000. Si está ordenada alfabéticamente, abrís por la mitad, ves "López", sabés que Martínez está después, y descartás la mitad de una. Con 1.000 contactos lo encontrás en 10 pasos. Los dos métodos son correctos; uno es muchísimo más eficiente. Esa diferencia es de lo que trata la materia.

BásicoRecursión

Una función es recursiva cuando se llama a sí misma con un problema más chico. D&C, Programación Dinámica, Backtracking y DFS son todos recursivos, así que esto es la base de media materia.

En la vida real

Estás en el cine, a oscuras, y querés saber en qué fila estás. Le preguntás al de adelante "¿en qué fila estás vos?". Él no sabe, así que le pregunta al de adelante, y así. El de la primera fila no le pregunta a nadie: sabe que está en la fila 1. Le contesta "1" al de atrás, ese le contesta "2" al suyo, y la respuesta vuelve sumando 1 en cada paso hasta llegar a vos.

Ahí están las dos partes de toda recursión: el caso base (el de la primera fila, que responde sin preguntar) y el caso recursivo (todos los demás, que delegan un problema más chico y usan la respuesta).

Toda función recursiva necesita:

  1. Caso base: una entrada tan chica que se responde directo, sin llamarse. Sin caso base, la función se llama para siempre y Java tira StackOverflowError.
  2. Caso recursivo: se llama a sí misma con un problema más chico, que tiene que acercarse al caso base.
  3. Confiar en la llamada: al escribirla, asumí que la llamada recursiva devuelve la respuesta correcta para el problema chico y preguntate solo cómo usarla para el grande.
Factorial.java
// 4! = 4 · 3 · 2 · 1 = 24
int factorial(int n) {
    if (n <= 1) {
        return 1;                    // caso base
    }
    return n * factorial(n - 1);     // caso recursivo: n! = n · (n-1)!
}

Traza de factorial(4)

BAJADA (cada llamada espera a la siguiente)
factorial(4) = 4 * factorial(3)
                   factorial(3) = 3 * factorial(2)
                                      factorial(2) = 2 * factorial(1)
                                                         factorial(1) = 1   ← caso base

SUBIDA (las respuestas vuelven)
                                                         factorial(1) → 1
                                      factorial(2) = 2 * 1 → 2
                   factorial(3) = 3 * 2 → 6
factorial(4) = 4 * 6 → 24

IntermedioLa pila de llamadas

¿Cómo "se acuerda" Java de que factorial(4) está esperando? Cada llamada se apila en la pila de llamadas (call stack) con sus variables. Cuando una termina, se desapila y le devuelve el resultado a la que está debajo. Es una pila de platos: el último que pusiste es el primero que sacás.

Pila de llamadasfactorial(n)

De acá salen dos cosas importantes para el parcial:

  • La recursión usa memoria: con n llamadas apiladas a la vez, usa O(n) de memoria de pila, aunque no declares ningún arreglo.
  • Cuántas llamadas hace determina la complejidad. factorial hace 1 llamada por nivel y n niveles: O(n). Si una función hace dos llamadas por nivel (como Fibonacci), la cantidad se duplica en cada nivel y explota. Eso lo vemos en Recurrencias.

Más ejemplos para practicar el "confiar en la llamada"

// suma de los dígitos: 4721 → 4 + 7 + 2 + 1 = 14
int sumaDigitos(int n) {
    if (n < 10) {
        return n;                            // un solo dígito

    return n % 10 + sumaDigitos(n / 10);     // último dígito + el resto

// suma de un arreglo desde la posición i
int suma(int[] v, int i) {
    if (i == v.length) {
        return 0;                            // no quedan elementos
    }
    return v[i] + suma(v, i + 1);

// invertir un String: "hola" → "aloh"
String invertir(String s) {
    if (s.length() <= 1) {
        return s;
    }
    return invertir(s.substring(1)) + s.charAt(0);
}

0.1

Jugando a "mayor o menor" con un número del 1 al 1.000, ¿cuántas preguntas necesitás como máximo? ¿Y del 1 al 1.000.000?

Ver resolución

Cada pregunta parte el rango a la mitad, así que hacen falta ⌈log2 n⌉. Como 210 = 1.024 ≥ 1.000, alcanza con 10. Como 220 ≈ 1.048.576, alcanza con 20. Mil veces más números, solo el doble de preguntas.

0.2

¿Qué devuelve misterio(5)? Hacé la traza.

Java
int misterio(int n) {
    if (n == 0) return 0;
    return n + misterio(n - 1);
}
Ver resolución
misterio(5) = 5 + misterio(4)
            = 5 + 4 + misterio(3)
            = 5 + 4 + 3 + misterio(2)
            = 5 + 4 + 3 + 2 + misterio(1)
            = 5 + 4 + 3 + 2 + 1 + misterio(0)
            = 5 + 4 + 3 + 2 + 1 + 0 = 15

15 Suma de 1 a n. Hace n + 1 llamadas: O(n).

0.3

¿Qué pasa con misterio(-1)? ¿Cómo lo arreglás?

Ver resolución

Llama a misterio(-2), misterio(-3)… nunca llega a 0, porque el problema se aleja del caso base. Las llamadas se apilan hasta que se llena la pila: StackOverflowError. Se arregla cambiando el caso base a if (n <= 0) return 0;.

0.4

¿Qué estructura usás en cada caso? (a) El botón "deshacer" de un editor. (b) Atender llamados en un call center por orden de llegada. (c) Un sistema de turnos de emergencias. (d) Guardar el resultado de cada subproblema ya calculado.

Ver resolución
  1. Pila: se deshace lo último que hiciste.
  2. Cola: el primero que llamó es el primero atendido.
  3. Cola de prioridad: pasa el más grave, no el que llegó antes.
  4. Arreglo o matriz (o un HashMap): es la "memoria" de la Programación Dinámica.
0.5

Escribí una función recursiva que cuente cuántas veces aparece x en un arreglo.

Ver resolución

Caso base: si no quedan elementos, aparece 0 veces. Caso recursivo: miro el primero (cuenta 1 si es x) y confío en que la llamada me cuenta el resto.

Java
int contar(int[] v, int x, int i) {
    if (i == v.length) {
        return 0;
    }
    int esteCuenta = (v[i] == x) ? 1 : 0;
    return esteCuenta + contar(v, x, i + 1);
}
// contar(new int[]{3, 1, 3, 3, 2}, 3, 0) → 3

Complejidad temporal

La complejidad no mide cuántos segundos tarda un programa. Mide cómo crece la cantidad de operaciones cuando crece el tamaño de la entrada n. Responde una sola pregunta: ¿cómo escala el algoritmo cuando el problema se hace más grande?

RutaLa idea→Contar operaciones→Mejor y peor caso→Reglas para calcular→O, Ω, Θ formales→Sumas→Ordenamientos simples→Trampas

BásicoLa idea: ¿qué pasa si duplico la entrada?

Los segundos dependen de la compu, del lenguaje y de lo que esté corriendo al mismo tiempo. Contar operaciones no depende de nada de eso. La pregunta que importa es: si la entrada se duplica, ¿cuánto más trabajo hay?

En la vida real
  • O(1), constante: mirar la hora en el reloj. Tarda lo mismo si el día tiene 10 o 1.000 eventos. Como acceder a v[5].
  • O(log n), logarítmica: buscar una palabra en un diccionario de papel abriendo por la mitad. Si el diccionario tiene el doble de páginas, hacés una apertura más.
  • O(n), lineal: repartir volantes casa por casa. El doble de casas, el doble de trabajo.
  • O(n log n): ordenar un mazo grande de cartas con un método inteligente (partir en pilas, ordenarlas, juntarlas). Un poco más que lineal.
  • O(n2), cuadrática: en una fiesta, que cada invitado salude a todos los demás. El doble de invitados, cuatro veces más saludos.
  • O(2n), exponencial: probar todas las combinaciones de ingredientes para una pizza (cada uno va o no va). Un ingrediente más duplica las combinaciones.
  • O(n!), factorial: probar todos los órdenes posibles para visitar n clientes en un día. Con 10 clientes ya son 3.628.800 órdenes.

BásicoContar operaciones: T(n)

T(n) es la cantidad de operaciones elementales que hace el algoritmo con una entrada de tamaño n. Una operación elemental es cualquier cosa que tarda tiempo constante: una suma, una comparación, una asignación, acceder a v[i].

Suma.java
int suma(int[] v) {
    int total = 0;                        // 1 operación
    for (int i = 0; i < v.length; i++) {  // n vueltas
        total += v[i];                    // 1 operación por vuelta
    }
    return total;                         // 1 operación
}

A grandes rasgos: T(n) = n + 2. Cuando n es grande, el + 2 no pesa nada, y tampoco importaría si cada vuelta costara 3 operaciones en vez de 1. Nos quedamos con la forma de crecimiento: O(n).

Las dos reglas que salen de acá y usás siempre:

  • Las constantes no importan: 3n, n/2 y 100n son todos O(n).
  • Se queda el término que más crece: 3n2 + 5n + 2 es O(n2).

IntermedioMejor caso, peor caso y caso promedio

Para el mismo n, el algoritmo puede tardar distinto según cómo venga la entrada. Con la búsqueda lineal (recorrer el arreglo hasta encontrar x):

  • Mejor caso: x está en la primera posición. 1 comparación.
  • Peor caso: x está última o no está. n comparaciones.
  • Caso promedio: si puede estar en cualquier lugar con igual probabilidad, n/2 en promedio, que sigue siendo lineal.
En la vida real

Buscás las llaves en los bolsillos de una campera con 6 bolsillos. Mejor caso: están en el primero que revisás. Peor caso: en el último (o no están). Si te preguntan "¿cuánto tardás en encontrar las llaves?", la respuesta honesta es "como mucho, 6 bolsillos". Eso es el peor caso: una garantía.

Cuando en un parcial te preguntan "¿qué complejidad tiene?" sin aclarar, casi siempre esperan el peor caso.

IntermedioReglas para calcular la complejidad de un código

  1. Operaciones simples (+, -, asignaciones, comparaciones, acceso a arreglo): O(1).
  2. Un bucle: cantidad de vueltas × lo que cuesta el cuerpo.
  3. Bucles anidados: se multiplican. Dos for de n: O(n2). Tres: O(n3).
  4. Bloques uno después del otro: se suman y queda el mayor. Un for de n y después otro de n: O(n).
  5. Bucles que multiplican o dividen la variable (i *= 2, i /= 2): O(log n).
  6. Llamadas a métodos: cuentan lo que cuesta el método, no 1. lista.contains(x) en un ArrayList recorre la lista: es O(n).
  7. Funciones recursivas: se plantea la recurrencia y se resuelve (Unidad 2).

Un bucle simple

Java
for (int i = 0; i < n; i++) {
    System.out.println(i);
}

El cuerpo se ejecuta n veces: O(n)

Dos bucles anidados

Java
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        System.out.println(i + " " + j);
    }
}

Por cada una de las n vueltas de afuera, el de adentro da n. Pensalo como una planilla de n filas por n columnas: la recorrés entera. O(n²)

Bucle "triangular" (el de adentro depende del de afuera)

Java
for (int i = 0; i < n; i++) {
    for (int j = 0; j < i; j++) {
        System.out.println(i + " " + j);
    }
}

El de adentro da 0, 1, 2, … hasta n − 1 vueltas. Total: 0 + 1 + … + (n − 1) = n(n − 1)/2. Es la mitad de la planilla (un triángulo), pero la mitad de n2 sigue siendo cuadrático. O(n²)

En la vida real

Es exactamente la fiesta de los saludos: si cada par de invitados se saluda una vez, el primero saluda a nadie nuevo, el segundo al primero, el tercero a los dos anteriores… Con 10 invitados son 45 saludos; con 20 son 190. Duplicar la gente cuadruplica (aproximadamente) los saludos.

Bucle que duplica

Java
for (int i = 1; i < n; i *= 2) {
    System.out.println(i);
}

i toma los valores 1, 2, 4, 8, …, 2k. Corta cuando 2k ≥ n, o sea cuando k = log2 n. O(log n)

Regla mental

Siempre que veas i *= 2, i /= 2, n /= 3 o "parto el problema a la mitad", pensá inmediatamente en logaritmos, no necesariamente en búsqueda binaria.

AvanzadoLas tres notaciones: O, Ω y Θ

En la vida real

Te preguntan cuánto tardás en llegar a la facu. "Como mucho una hora" es una cota superior (Big O). "Como mínimo 30 minutos" es una cota inferior (Omega). "Entre 40 y 50 minutos, siempre" es una cota ajustada (Theta): sabés el orden exacto.

NotaciónQué esSe leeDefinición

"Desde algún n0" significa que solo nos importa lo que pasa con entradas grandes. Para n chicos puede pasar cualquier cosa.

Ajuste a tus notas

En tus apuntes quedó "Big O = peor caso" y "Omega = mejor caso". En la práctica se usa así y para el parcial suele alcanzar, pero son dos cosas distintas: los casos (mejor/peor/promedio) dicen qué entrada miramos, y las notaciones (O/Ω/Θ) dicen qué tipo de cota damos sobre esa entrada. El peor caso de la búsqueda lineal es Θ(n) y su mejor caso es Θ(1). Decir "la búsqueda lineal es O(n)" es correcto porque en ningún caso supera lo lineal.

Ejemplo de la definición

¿Es f(n) = 3n2 + 5n + 2 de orden O(n2)? Hay que encontrar c y n0. Con c = 4 necesitamos 3n2 + 5n + 2 ≤ 4n2, o sea n2 − 5n − 2 ≥ 0, que vale desde n = 6 (36 − 30 − 2 = 4 ≥ 0). Con c = 4 y n0 = 6 se cumple. Sí, es O(n²)

Y no es O(n): haría falta 3n2 ≤ c·n, o sea 3n ≤ c, y eso falla apenas n > c/3. No existe constante que aguante para siempre.

Suma aritmética

Sn = n(a1 + an) / 2cantidad de términos × (primero + último) / 2

Para 1 + 2 + … + n: hay n términos, el primero es 1 y el último n, así que da n(n + 1)/2. El truco de Gauss: escribí la suma al derecho y al revés, una debajo de la otra. Cada columna suma n + 1, hay n columnas, y contaste todo dos veces.

  1  +   2   +   3   + ... +   n
  n  + (n-1) + (n-2) + ... +   1
───────────────────────────────────
(n+1) + (n+1) + (n+1) + ... + (n+1)   = n·(n+1)   → la suma es la mitad

Suma geométrica

∑k=0∞ a rk = a / (1 − r),   |r| < 1cada término es el anterior multiplicado por r

Sirve para las sumas que se achican: n + n/2 + n/4 + … es a = n, r = 1/2, y da como mucho n / (1 − 1/2) = 2n. Para las que crecen (1 + 2 + 4 + … + 2k) se usa la versión finita: da 2k+1 − 1, menos del doble del último término.

En la vida real

Comés media pizza, después la mitad de lo que queda, después la mitad de eso… Nunca comés más de una pizza entera. Eso es la geométrica que se achica: por más términos que agregues, la suma no pasa del doble del primero. Conclusión para el parcial: en una suma geométrica manda el término más grande.

AvanzadoAnalizando algoritmos completos: ordenamientos simples

Antes de los ordenamientos rápidos de D&C conviene ver los simples, que son O(n2), para tener contra qué comparar.

Burbuja

Recorre el arreglo comparando vecinos y los intercambia si están al revés. Después de cada pasada, el más grande "burbujea" hasta el final.

Burbuja.java
void burbuja(int[] v) {
    int n = v.length;
    for (int pasada = 0; pasada < n - 1; pasada++) {
        boolean huboCambio = false;
        for (int j = 0; j < n - 1 - pasada; j++) {
            if (v[j] > v[j + 1]) {
                int aux = v[j];
                v[j] = v[j + 1];
                v[j + 1] = aux;
                huboCambio = true;
            }
        }
        if (!huboCambio) {
            break;    // ya está ordenado
        }
    }
}
  • Peor caso (ordenado al revés): (n − 1) + (n − 2) + … + 1 = n(n − 1)/2 comparaciones → O(n2). Con [5, 1, 4, 2, 8] hace 10 comparaciones y 4 intercambios.
  • Mejor caso (ya ordenado): gracias al huboCambio, hace una sola pasada sin cambios y corta → O(n). Sin esa bandera sería O(n2) siempre.

Inserción

Como ordenar las cartas de tu mano: tomás la siguiente carta y la vas corriendo hacia la izquierda hasta que quede en su lugar.

Insercion.java
void insercion(int[] v) {
    for (int i = 1; i < v.length; i++) {
        int actual = v[i];
        int j = i - 1;
        while (j >= 0 && v[j] > actual) {
            v[j + 1] = v[j];    // corro el mayor a la derecha
            j--;
        }
        v[j + 1] = actual;
    }
}
[5, 2, 4, 6, 1, 3]
i=1  inserto 2 → [2, 5, 4, 6, 1, 3]
i=2  inserto 4 → [2, 4, 5, 6, 1, 3]
i=3  inserto 6 → [2, 4, 5, 6, 1, 3]   (ya estaba bien: 0 corrimientos)
i=4  inserto 1 → [1, 2, 4, 5, 6, 3]   (corre hasta el principio)
i=5  inserto 3 → [1, 2, 3, 4, 5, 6]

Peor caso (al revés): cada elemento corre hasta el principio, O(n2). Mejor caso (ordenado): el while no entra nunca, O(n).

Complejidad espacial

Lo mismo se puede medir para la memoria extra que usa el algoritmo (sin contar la entrada). Burbuja e inserción usan un par de variables: O(1). MergeSort usa un arreglo auxiliar: O(n). Una función recursiva con n llamadas apiladas usa O(n) de pila.

ParcialTrampas típicas

Dos for anidados no siempre son n²

Mirá de qué depende cada límite. for (j = 0; j < 100; j++) adentro de un for de n da 100n = O(n). Y un for con j *= 2 adentro de uno de n da O(n log n).

Un for solo puede ser n²

Si adentro del for llamás a algo que recorre, el costo se multiplica:

Java
for (int x : v) {
    if (!lista.contains(x)) {   // contains recorre la lista: O(n)
        lista.add(x);
    }
}

Parece lineal, pero es O(n2). Con un HashSet en vez de ArrayList, contains es O(1) y queda lineal.

Big O es una cota superior

"n ∈ O(n2)" es verdadero: n no crece más rápido que n2. Es una cota floja, pero válida. Si te piden la ajustada, es Θ(n).

Recurrencias y Teorema Maestro

Cuando una función es recursiva no podés contar vueltas de un for: el costo depende de sí mismo. Lo que se hace es escribir una recurrencia, una ecuación que dice cuánto cuesta T(n) en función de lo que cuestan las llamadas más chicas, y después resolverla.

RutaLa idea→Armar la recurrencia→Desenrollar→Árbol de recursión→Teorema Maestro→Cuándo no aplica

BásicoLa idea: una empresa que delega

En la vida real

Una gerenta recibe un trabajo de tamaño n. Lo parte en pedazos, se los da a a empleados (cada uno recibe un pedazo de tamaño n/b), y ella se queda haciendo un trabajo propio de organizar y juntar, que le cuesta f(n). Cada empleado hace lo mismo con su pedazo: lo parte, lo delega y junta. Así hasta que los pedazos son tan chicos que se hacen directo.

¿Cuánto trabajo hay en total en la empresa? Eso es lo que resuelve una recurrencia. Y el Teorema Maestro contesta una pregunta muy concreta: ¿quién trabaja más en total, la gerenta de arriba o la enorme cantidad de empleados de abajo?

T(n) = a · T(n/b) + f(n)lo que cuestan los a subproblemas + lo que cuesta dividir y combinar

BásicoCómo se arma la recurrencia a partir del código

  1. Cuántas llamadas recursivas hace cada ejecución → a.
  2. De qué tamaño es cada llamada: ¿la mitad (n/2)? ¿un tercio? ¿uno menos (n − 1)?
  3. Cuánto trabajo hace fuera de las llamadas (dividir, combinar, un for…) → f(n).
  4. Caso base: cuánto cuesta cuando ya no se llama (casi siempre constante, y no cambia el orden).

Búsqueda binaria recursiva

Java
boolean buscar(int[] v, int x, int ini, int fin) {
    if (ini > fin) return false;
    int medio = (ini + fin) / 2;
    if (v[medio] == x) return true;
    if (v[medio] > x) return buscar(v, x, ini, medio - 1);
    return buscar(v, x, medio + 1, fin);
}

Aunque aparecen dos buscar, en cada ejecución se hace una sola (es un if/else). Tamaño mitad, trabajo extra constante:
T(n) = T(n/2) + 1

MergeSort

Java
void mergeSort(int[] v, int ini, int fin) {
    if (ini >= fin) return;
    int medio = (ini + fin) / 2;
    mergeSort(v, ini, medio);
    mergeSort(v, medio + 1, fin);
    merge(v, ini, medio, fin); // O(n)
}

2 llamadas, cada una de la mitad, y el merge recorre todo:
T(n) = 2T(n/2) + n

Ojo

Contá las llamadas que se ejecutan, no las que aparecen escritas. En la binaria hay dos buscar en el código pero se ejecuta uno por vez. En f(n-1) + f(n-1) hay dos y se ejecutan las dos.

IntermedioMétodo 1: desenrollar (sustitución)

Reemplazás T por su definición una y otra vez hasta ver el patrón, lo escribís en función de un paso genérico k, y elegís k para llegar al caso base. Es el método que sirve cuando el problema se achica restando (n − 1), donde el Teorema Maestro no aplica.

Ejemplo 1: T(n) = T(n − 1) + 1 (factorial, recorrer una lista)

T(n) = T(n-1) + 1
     = T(n-2) + 1 + 1     = T(n-2) + 2
     = T(n-3) + 3
     = T(n-k) + k          ← patrón con k pasos
con k = n-1:  T(1) + n - 1  →  O(n)

Ejemplo 2: T(n) = T(n − 1) + n (QuickSort en el peor caso)

T(n) = T(n-1) + n
     = T(n-2) + (n-1) + n
     = T(n-3) + (n-2) + (n-1) + n
     = ...
     = T(1) + 2 + 3 + ... + (n-1) + n
     ≈ 1 + 2 + ... + n = n(n+1)/2      →  O(n²)

Ejemplo 3: T(n) = 2T(n − 1) + 1 (Torres de Hanoi)

T(n) = 2T(n-1) + 1
     = 2[2T(n-2) + 1] + 1         = 4T(n-2) + 2 + 1
     = 4[2T(n-3) + 1] + 2 + 1     = 8T(n-3) + 4 + 2 + 1
     = 2^k T(n-k) + (2^(k-1) + ... + 2 + 1)
con k = n-1:  2^(n-1)·T(1) + 2^(n-1) - 1     →  O(2ⁿ)

Dos llamadas que solo restan 1 duplican el trabajo en cada nivel: exponencial. Es lo que le pasa a Fibonacci recursivo (Unidad 5).

Ejemplo 4: T(n) = T(n/2) + 1 desenrollando

T(n) = T(n/2) + 1 = T(n/4) + 2 = T(n/8) + 3 = T(n/2^k) + k
llega a T(1) cuando n/2^k = 1  →  k = log₂ n   →   T(n) = 1 + log₂ n  →  O(log n)

IntermedioMétodo 2: árbol de recursión

Dibujás las llamadas como el organigrama de la empresa, anotás cuánto trabajo propio hace cada nodo, y sumás por niveles. Para T(n) = 2T(n/2) + n:

nivel 0:              n                         →  n
nivel 1:        n/2       n/2                   →  n
nivel 2:     n/4  n/4  n/4  n/4                 →  n
  ...                    ...                       ...
nivel log n:  1  1  1  1  ...  1  (n hojas)     →  n
─────────────────────────────────────────────────────────
log n niveles × n por nivel                     =  n log n

Cada nivel cuesta lo mismo (n) y hay log n niveles porque dividimos por 2 hasta llegar a 1. O(n log n)

Con otra recurrencia, el costo por nivel puede crecer o achicarse al bajar. Mirá T(n) = 4T(n/2) + n:

nivel 0:  1 nodo  de tamaño n     → n
nivel 1:  4 nodos de tamaño n/2   → 4·n/2  = 2n
nivel 2: 16 nodos de tamaño n/4   → 16·n/4 = 4n
nivel k: 4^k nodos de n/2^k        → 2^k · n      ← crece en cada nivel

Como los niveles crecen geométricamente, manda el último (las hojas): hay 4log2 n = n2 hojas. O(n²). Los empleados de abajo, que son muchísimos, hacen casi todo el trabajo.

AvanzadoMétodo 3: Teorema Maestro

Es la receta para resolver de una las recurrencias de la forma:

T(n) = a · T(n/b) + f(n)a ≥ 1: cantidad de llamadas recursivas · b > 1: en cuánto se divide el tamaño · f(n): trabajo fuera de las llamadas

Compara dos cosas: el trabajo de la raíz (la gerenta), f(n), contra el trabajo de las hojas (los empleados de abajo de todo), que es nlogb a. ¿De dónde sale ese número? El árbol tiene logb n niveles y en cada nivel los nodos se multiplican por a, así que hay alogb n = nlogb a hojas. El que pesa más, gana.

CasoCondiciónResultadoEn la empresa
1f(n) crece más lento que nlogb aΘ(nlogb a)Ganan las hojas: hay tantos empleados que su trabajo total domina.
2f(n) crece igual que nlogb aΘ(f(n) · log n)Empate: cada nivel de la empresa trabaja lo mismo, y hay log n niveles.
3f(n) crece más rápido que nlogb aΘ(f(n))Gana la raíz: la gerenta hace más que todo el resto junto.
Versión rápida (la que vas a usar el 95% de las veces)

Si f(n) = nd, compará el exponente d con logb a:

  • d < logb a → Θ(nlogb a)
  • d = logb a → Θ(nd log n)
  • d > logb a → Θ(nd)

Una constante es n0 (d = 0), n es n1 y √n es n1/2. La tabla de logaritmos útiles está en Bases.

Karatsuba: T(n) = 3T(n/2) + n

a = 3, b = 2, d = 1. log2 3 ≈ 1,585. Como 1 < 1,585, caso 1: Θ(n^1,585). Mejor que la multiplicación de la escuela, que es n2 (ver Karatsuba).

El Teorema Maestro no aplica si…
  • El problema se achica restando: T(n − 1), T(n − 2). Ahí desenrollás.
  • Las llamadas son de tamaños distintos: T(n/3) + T(2n/3) + n. Ahí va árbol de recursión (da n log n: cada nivel suma como mucho n).

Divide y Conquista

"Divido el problema, resuelvo las partes y combino las soluciones." Partís el problema en subproblemas más chicos e independientes del mismo tipo, los resolvés recursivamente y juntás los resultados.

RutaLa idea→Búsqueda binaria→MergeSort→QuickSort→Karatsuba→Para el parcial

BásicoLa idea

En la vida real

Tenés que ordenar alfabéticamente 200 exámenes y tenés dos ayudantes. Les das 100 a cada uno y les decís "ordenalos". Cada ayudante hace lo mismo con dos ayudantes suyos, y así, hasta que a alguien le toca un solo examen (que ya está ordenado). Cuando te devuelven tus dos pilas ordenadas, las juntás mirando el de arriba de cada pila y sacando el que va primero.

Nadie ordenó 200 exámenes de golpe: cada uno resolvió un problema chico, y juntar dos pilas ya ordenadas es fácil. Eso es MergeSort, y es la idea de toda la técnica.

  1. Caso base: si el problema es lo bastante chico (un elemento, rango vacío), se resuelve directo.
  2. Dividir: partir en subproblemas más chicos del mismo tipo (generalmente mitades).
  3. Conquistar: resolver cada subproblema con una llamada recursiva.
  4. Combinar: armar la solución del problema original con las soluciones de las partes.
Esquema general
Solucion resolver(Problema p) {
    if (esChico(p)) {
        return resolverDirecto(p);       // caso base
    }
    List<Problema> partes = dividir(p);  // dividir
    List<Solucion> sols = new ArrayList<>();
    for (Problema parte : partes) {
        sols.add(resolver(parte));       // conquistar
    }
    return combinar(sols);               // combinar
}

La complejidad sale casi siempre con el Teorema Maestro: a es la cantidad de partes, b en cuánto se achican, f(n) lo que cuesta dividir más combinar.

Cuándo sirve D&C

Cuando las partes son independientes: ordenar la mitad izquierda no necesita saber nada de la derecha. Si los subproblemas se repiten (como en Fibonacci, donde fib(3) aparece muchas veces), D&C recalcula lo mismo una y otra vez y conviene Programación Dinámica.

BásicoBúsqueda binaria

En la vida real

Buscar "murciélago" en un diccionario de papel: lo abrís por la mitad, caés en la "L", sabés que la M está después y te olvidás de toda la primera mitad. Volvés a abrir por la mitad de lo que queda. Nunca leés el diccionario entero. Funciona solo porque está ordenado: en un diccionario desordenado, ver la "L" no te diría nada.

Comparás x con el elemento del medio. Si es igual, encontraste. Si el del medio es más grande, x solo puede estar a la izquierda (todo lo de la derecha es todavía más grande), así que descartás la mitad derecha. Si es más chico, descartás la izquierda. En cada paso tirás la mitad de lo que queda.

Es una versión simplificada de D&C (a veces se la llama "reduce y vencerás"): divide, pero resuelve una sola de las partes y no combina nada.

BusquedaVector.java
public class BusquedaVector {

    public static boolean pertenece(int[] vector, int x) {
        int inicio = 0;
        int fin = vector.length - 1;

        while (inicio <= fin) {
            int medio = inicio + (fin - inicio) / 2;

            if (vector[medio] == x) {
                return true;
            } else if (vector[medio] > x) {
                fin = medio - 1;      // busca en la mitad izquierda
            } else {
                inicio = medio + 1;   // busca en la mitad derecha
            }
        }
        return false;                 // no se encontró
    }
}

¿Por qué inicio + (fin - inicio) / 2 y no (inicio + fin) / 2? Dan lo mismo, pero si inicio y fin son enormes la suma puede pasarse del máximo de un int (overflow). La primera forma nunca se pasa.

Complejidad: T(n) = T(n/2) + 1 → O(log n). Con un millón de elementos son como mucho 20 comparaciones.

IntermedioMergeSort

Divide fácil, combina con trabajo. Partís el arreglo por la mitad sin mirar los valores, ordenás cada mitad recursivamente y después las intercalás (merge).

El merge, a mano

Es lo de las dos pilas de exámenes. Tenés dos listas ya ordenadas. Mirás el primero de cada una, sacás el menor y lo ponés en el resultado. Repetís. Cuando una lista se vacía, copiás lo que queda de la otra (que ya está ordenado).

MergeSort.java
public static void mergeSort(int[] v, int inicio, int fin) {
    // CASO BASE
    if (inicio >= fin) {
        return;
    }
    int medio = (inicio + fin) / 2;

    // DIVIDIR
    mergeSort(v, inicio, medio);
    mergeSort(v, medio + 1, fin);

    // COMBINAR
    merge(v, inicio, medio, fin);
}

public static void merge(int[] v, int inicio, int medio, int fin) {
    int[] auxiliar = new int[fin - inicio + 1];
    int i = inicio;       // recorre la mitad izquierda
    int j = medio + 1;    // recorre la mitad derecha
    int k = 0;            // posición en auxiliar

    while (i <= medio && j <= fin) {
        if (v[i] <= v[j]) {
            auxiliar[k] = v[i];
            i++;
        } else {
            auxiliar[k] = v[j];
            j++;
        }
        k++;
    }
    // Copiar sobrantes de la izquierda
    while (i <= medio) {
        auxiliar[k] = v[i];
        i++;
        k++;
    }
    // Copiar sobrantes de la derecha
    while (j <= fin) {
        auxiliar[k] = v[j];
        j++;
        k++;
    }
    // Copiar resultado al arreglo original
    for (i = inicio, k = 0; i <= fin; i++, k++) {
        v[i] = auxiliar[k];
    }
}

Complejidad: T(n) = 2T(n/2) + n → O(n log n) en todos los casos: siempre parte justo a la mitad, sin importar los datos. Su contra: usa un arreglo auxiliar, O(n) de memoria extra. El <= en v[i] <= v[j] lo hace estable: si hay dos iguales, sale primero el de la izquierda, así que no cambia su orden relativo.

IntermedioQuickSort

En la vida real

La profe de gimnasia quiere ordenar a los chicos por altura. Elige a uno, Juan (el pivote), y dice: "los más bajos que Juan, a su izquierda; los más altos, a su derecha". Juan ya quedó en su lugar definitivo. Después repite lo mismo con el grupo de la izquierda y con el de la derecha, cada uno por su lado. No hace falta juntar nada al final: si cada grupo está ordenado, la fila entera está ordenada.

¿Qué pasa si elige justo al más alto como pivote? Todos van a la izquierda, la derecha queda vacía, y no avanzó casi nada. Ese es el peor caso de QuickSort.

Particiona con trabajo, casi no combina: lo opuesto a MergeSort.

QuickSort.java
public class QuickSort {

    public static void quickSort(int[] v, int inicio, int fin) {
        if (inicio < fin) {
            int pivote = partition(v, inicio, fin);
            quickSort(v, inicio, pivote - 1);
            quickSort(v, pivote + 1, fin);
        }
    }

    // Lomuto: el pivote es el último elemento
    public static int partition(int[] v, int inicio, int fin) {
        int pivote = v[fin];
        int i = inicio - 1;   // último índice de la zona "<= pivote"

        for (int j = inicio; j < fin; j++) {
            if (v[j] <= pivote) {
                i++;
                int aux = v[i];
                v[i] = v[j];
                v[j] = aux;
            }
        }
        // el pivote va justo después de la zona de menores
        int aux = v[i + 1];
        v[i + 1] = v[fin];
        v[fin] = aux;

        return i + 1;
    }
}

Cómo funciona el partition de Lomuto

Pensalo con dos dedos. j recorre el arreglo de izquierda a derecha mirando cada elemento. i marca dónde termina la zona de los "chicos" (los ≤ pivote). Arranca en inicio − 1 porque al principio esa zona está vacía. Cada vez que j encuentra un chico, agranda la zona (i++) y lo mete adentro con un swap. Al final, el pivote se cambia con v[i + 1], que es el primer "grande".

AvanzadoComplejidad y el problema del pivote

  • Mejor caso / promedio: el pivote cae más o menos en el medio y parte en dos mitades parecidas (50-50, o incluso 30-70). T(n) = 2T(n/2) + n → O(n log n).
  • Peor caso: el pivote es siempre el mínimo o el máximo. Un lado queda vacío y el otro con n − 1 elementos. T(n) = T(n − 1) + n → n + (n − 1) + … = n(n − 1)/2 → O(n2).

Con Lomuto, el peor caso aparece con un arreglo ya ordenado (el último es siempre el máximo) o ordenado al revés. Lo "más fácil" es lo que peor le sale.

AvanzadoKaratsuba (multiplicación rápida)

Multiplicar dos números de n dígitos "como en la escuela" cuesta O(n2): cada dígito de uno por cada dígito del otro. Karatsuba lo baja con D&C y un truco algebraico. Partís cada número en dos mitades de m dígitos:

x = a · 10m + b     y = c · 10m + d1234 = 12 · 100 + 34
x · y = ac · 102m + (ad + bc) · 10m + bd

Así hacen falta 4 multiplicaciones de la mitad de tamaño (ac, ad, bc, bd), y 4T(n/2) + n sigue siendo n2. El truco: el término del medio sale con una sola multiplicación más.

(a + b)(c + d) − ac − bd = ad + bcac y bd ya los tenías calculados

3 multiplicaciones en vez de 4. Las sumas y los corrimientos (multiplicar por potencias de 10 es agregar ceros) son lineales. T(n) = 3T(n/2) + n → O(n^log₂3) ≈ O(n^1,585). Parece poco, pero con números de un millón de dígitos son unas 300 veces menos operaciones (n2 / n1,585 = n0,415).

Karatsuba.java
public static long karatsuba(long x, long y) {
    if (x < 10 || y < 10) {
        return x * y;                      // caso base: un dígito
    }
    int n = Math.max(Long.toString(x).length(), Long.toString(y).length());
    int m = n / 2;
    long p = (long) Math.pow(10, m);

    long a = x / p, b = x % p;             // x = a·10^m + b
    long c = y / p, d = y % p;             // y = c·10^m + d

    long ac = karatsuba(a, c);
    long bd = karatsuba(b, d);
    long medio = karatsuba(a + b, c + d) - ac - bd;   // ad + bc

    return ac * p * p + medio * p + bd;
}

Java
public static int primeraPosicion(int[] v, int x) {
    int inicio = 0, fin = v.length - 1, resultado = -1;
    while (inicio <= fin) {
        int medio = inicio + (fin - inicio) / 2;
        if (v[medio] == x) {
            resultado = medio;      // candidato
            fin = medio - 1;        // sigo buscando a la izquierda
        } else if (v[medio] > x) {
            fin = medio - 1;
        } else {
            inicio = medio + 1;
        }
    }
    return resultado;
}

Sigue siendo O(log n): el rango se parte a la mitad en cada vuelta igual que antes.

3.11

Explicá por qué una mala elección del pivote hace que QuickSort pase de O(n log n) a O(n2).

Ver resolución

El partition siempre cuesta lineal en el tamaño del subarreglo. Lo que cambia es cuántos niveles de recursión hay. Si el pivote parte más o menos al medio, el tamaño se divide en cada nivel: hay log n niveles con trabajo total n cada uno, n log n. Si el pivote es siempre un extremo, cada nivel solo saca el pivote, quedan particiones de 0 y n − 1, y hay n niveles: n + (n − 1) + … + 1 = n(n − 1)/2.

Greedy (algoritmos voraces)

En cada paso elegís la opción que parece mejor en ese momento, la tomás de forma definitiva y no volvés atrás. No pensás en las consecuencias futuras.

RutaLa idea→Cambio de monedas→Actividades→Mochila fraccionaria→Por qué funciona→Cuándo falla

BásicoLa idea

En la vida real

Estás manejando sin GPS hacia un lugar que ves a lo lejos. En cada esquina doblás hacia donde el lugar "parece" más cerca. Muchas veces llegás perfecto. Pero a veces esa decisión te mete en una calle sin salida, y como el método no vuelve atrás, terminás dando una vuelta enorme. Greedy es eso: decisiones locales que parecen buenas. A veces llevan al óptimo y a veces no.

Greedy responde la pregunta "¿cuál es la mejor opción que puedo tomar ahora?", cuando el problema en realidad pregunta "¿cuál es la mejor solución considerando todo?". Si las dos respuestas coinciden, Greedy es perfecto y muy rápido. Si no, da una solución que funciona pero no es la óptima.

  1. Tenemos un problema.
  2. Elegimos la mejor opción disponible según un criterio (la moneda más grande, la actividad que termina antes, el objeto con mejor valor/peso…).
  3. Tomamos esa decisión definitivamente: no se deshace nunca.
  4. Reducimos el problema (lo que queda por resolver).
  5. Volvemos a elegir con el mismo criterio, hasta construir la solución.

La parte difícil de Greedy no es el código (casi siempre es un sort y un for): es elegir el criterio correcto y saber justificar que funciona.

BásicoCambio de monedas

En la vida real

El kiosquero te tiene que dar $63 de vuelto con la menor cantidad de monedas y billetes. Sin pensarlo, agarra el más grande que entra (25), de nuevo 25, después 10, y completa con tres de 1. Eso es Greedy, y con las monedas de siempre anda perfecto.

Criterio: usar siempre la moneda más grande que entre en lo que falta.

CambioMonedas.java
// monedas ordenadas de mayor a menor
public static int cambioMonedas(int[] monedas, int monto) {
    int cantidad = 0;
    for (int moneda : monedas) {
        while (monto >= moneda) {
            monto -= moneda;
            cantidad++;
        }
    }
    return cantidad;
}

Con {25, 10, 5, 1} y monto 63: 25 + 25 + 10 + 1 + 1 + 1 = 6 monedas, que es el óptimo. Con los sistemas de monedas "normales" (llamados canónicos) Greedy siempre da el óptimo.

Pero con monedas {4, 3, 1} y monto 6:

  • Greedy agarra el 4 (es la más grande que entra), quedan 2, y completa con 1 + 1. 3 monedas.
  • El óptimo es 3 + 3. 2 monedas.

Haber tomado el 4 fue buena idea "ahora", pero arruinó el resto. Ese es el riesgo de Greedy. Para este caso hay que usar Programación Dinámica.

public static List<Actividad> seleccionar(List<Actividad> actividades) {
    actividades.sort(Comparator.comparingInt(a -> a.fin));

    List<Actividad> resultado = new ArrayList<>();
    Actividad ultima = actividades.get(0);
    resultado.add(ultima);

    for (int i = 1; i < actividades.size(); i++) {
        Actividad actual = actividades.get(i);
        if (actual.inicio >= ultima.fin) {   // no se superpone
            resultado.add(actual);
            ultima = actual;
        }
    }
    return resultado;
}

Complejidad: sort O(n log n) + una pasada O(n) = O(n log n). El >= importa: si una termina a las 4 y otra empieza a las 4, no se pisan.

En la vida real

Vas a una dietética con una bolsa que aguanta 50 kg, y todo se vende suelto: almendras, nueces, pasas. Querés llevarte el máximo valor. Obvio: primero lo que más vale por kilo, todo lo que haya; después lo siguiente; y cuando no te entra todo lo último, llevás la parte que entra. Como podés fraccionar, nunca desperdiciás lugar.

Criterio: ordenar por valor/peso de mayor a menor, meter enteros los que entren, y fraccionar el primero que no entre completo.

MochilaFraccionaria.java
class Objeto {
    int peso, valor;
    Objeto(int peso, int valor) {
        this.peso = peso;
        this.valor = valor;
    }
}

public static double mochilaFraccionaria(List<Objeto> objetos, int capacidad) {
    // mayor valor/peso primero
    objetos.sort((a, b) -> Double.compare(
            (double) b.valor / b.peso,
            (double) a.valor / a.peso));

    double valorTotal = 0;
    int capacidadRestante = capacidad;

    for (Objeto objeto : objetos) {
        if (objeto.peso <= capacidadRestante) {
            capacidadRestante -= objeto.peso;
            valorTotal += objeto.valor;
        } else {
            double fraccion = (double) capacidadRestante / objeto.peso;
            valorTotal += objeto.valor * fraccion;
            break;
        }
    }
    return valorTotal;
}

AvanzadoPor qué funciona: las dos propiedades

Propiedad de elección greedy

Podés tomar la decisión localmente óptima sin perder la posibilidad de llegar al óptimo global. O sea: existe alguna solución óptima que incluye tu primera elección.

Subestructura óptima

Después de elegir, lo que queda es el mismo problema más chico, y su solución óptima, junto con tu elección, da el óptimo del problema completo.

El argumento de intercambio (para demostrar que sí funciona)

Es la forma estándar de justificar un Greedy. Para actividades:

  1. Sea g la actividad que termina primero (la que elige Greedy).
  2. Tomá cualquier solución óptima S, y sea o su primera actividad.
  3. Como g termina antes o igual que o, si reemplazás o por g en S, no chocás con ninguna de las otras (todas empezaban después de que terminaba o, así que también después de g).
  4. La nueva solución tiene la misma cantidad de actividades: también es óptima, y empieza con g. Elegir g no te hizo perder nada.
  5. Lo que queda (actividades que empiezan después de g) es el mismo problema más chico: se repite el razonamiento.

Para demostrar que NO funciona es mucho más fácil: alcanza con un contraejemplo concreto donde Greedy da peor que el óptimo.

Esquema general
Solucion greedy(List<Candidato> candidatos) {
    Solucion sol = new Solucion();
    ordenarSegunCriterio(candidatos);     // casi siempre hay un sort
    for (Candidato c : candidatos) {
        if (esFactible(sol, c)) {        // ¿lo puedo agregar sin romper nada?
            sol.agregar(c);               // decisión definitiva
        }
    }
    return sol;
}

Complejidad típica: O(n log n) por el sort.

Para que tenga sentido usar PD, el problema tiene que cumplir dos propiedades:

Subestructura óptima

La solución óptima del problema se arma a partir de soluciones óptimas de subproblemas más chicos. (Greedy también la necesita.)

Subproblemas superpuestos

Los mismos subproblemas aparecen una y otra vez. Esto es lo que la distingue de Divide y Conquista, donde los subproblemas son independientes.

IntermedioDos formas de hacer PD

En la vida real

Memoización es estudiar "a demanda" con un cuaderno al lado: cuando necesitás un resultado, primero te fijás si ya lo anotaste; si no, lo calculás y lo anotás. Tabulación es armar la tabla de multiplicar completa de antemano, de la fila 1 para arriba: cuando necesitás algo, ya está.

Top-down = Memoización

Se empieza por el problema grande, igual que la recursión, pero antes de calcular te fijás si ya está guardado.

Java
public static int fibonacci(int n, int[] memo) {
    if (n <= 1) {
        return n;
    }
    // ¿ya lo calculé?
    if (memo[n] != -1) {
        return memo[n];
    }
    // lo calculo y lo guardo
    memo[n] = fibonacci(n - 1, memo)
            + fibonacci(n - 2, memo);
    return memo[n];
}

Bottom-up = Tabulación

Se empieza por los problemas más chicos y se llena una tabla en orden. Sin recursión.

Java
public static int fibonacci(int n) {
    if (n <= 1) {
        return n;
    }
    int[] dp = new int[n + 1];
    dp[0] = 0;
    dp[1] = 1;

    for (int i = 2; i <= n; i++) {
        dp[i] = dp[i - 1] + dp[i - 2];
    }
    return dp[n];
}

Las dos son O(n): cada fib(i) se calcula una vez. La tabulación se puede optimizar guardando solo los dos últimos valores (O(1) de memoria), porque dp[i] solo usa dp[i-1] y dp[i-2].

IntermedioReceta para plantear cualquier PD

  1. Definí el estado: ¿qué significa dp[i] (o dp[i][w])? Escribilo en una oración en castellano. Es el paso más importante: si está mal definido, nada funciona.
  2. Recurrencia: ¿cómo se calcula dp[i] usando valores más chicos? Pensá en la última decisión: ¿cuál fue el último paso, el último objeto, la última moneda?
  3. Casos base: los valores que se saben sin calcular.
  4. Orden de llenado: que cada celda dependa solo de celdas ya llenas.
  5. Respuesta: ¿en qué celda queda el resultado?

IntermedioEscalera (subir de a 1 o de a 2)

Problema: una escalera de n escalones. En cada paso subís 1 o 2. ¿De cuántas formas distintas llegás arriba?

Aplicando la receta:

  1. Estado: dp[i] = cantidad de formas de llegar al escalón i.
  2. Última decisión: al escalón i llegás con un último paso de 1 (venías del i−1) o de 2 (venías del i−2). Son casos distintos, así que se suman: dp[i] = dp[i-1] + dp[i-2].
  3. Base: dp[0] = 1 (hay una forma de "estar en el piso": no moverse) y dp[1] = 1 (un solo paso de 1).
  4. Orden: de i = 2 para arriba. Respuesta: dp[n].
i      0  1  2  3  4  5
dp[i]  1  1  2  3  5  8

Para 5 escalones hay 8 formas. Es Fibonacci corrido un lugar: dp[n] = F(n + 1).

public static int escalera(int n) {
    int[] dp = new int[n + 1];
    dp[0] = 1;
    if (n >= 1) {
        dp[1] = 1;
    }
    for (int i = 2; i <= n; i++) {
        dp[i] = dp[i - 1] + dp[i - 2];
    }
    return dp[n];

AvanzadoMochila 0/1

En la vida real

Te mudás y en el baúl del auto entran 50 kg. Tenés cosas con distinto peso y distinto valor para vos (la tele, la compu, la bici…), y ninguna se puede partir. ¿Qué llevás en este viaje? Para cada cosa la pregunta es binaria: la llevo o no la llevo. Ya vimos que agarrar primero lo de mejor valor/peso puede fallar.

  1. Estado: dp[i][w] = el mejor valor posible usando solo los primeros i objetos, con una mochila de capacidad w.
  2. Última decisión (sobre el objeto i):
    • No llevarlo: me quedo con lo mejor que lograba sin él, dp[i-1][w].
    • Llevarlo (solo si entra, peso_i ≤ w): gano valor_i, pero me queda w − peso_i de lugar para los objetos anteriores: valor_i + dp[i-1][w - peso_i].
    Me quedo con la mejor de las dos.
  3. Base: dp[0][w] = 0 (sin objetos no hay valor) y dp[i][0] = 0 (sin capacidad tampoco).
  4. Orden: fila por fila, de izquierda a derecha. Respuesta: dp[n][W].
dp[i][w] = max( dp[i−1][w],  valori + dp[i−1][w − pesoi] )la segunda opción solo si pesoi ≤ w

¿Por qué dp[i-1] y no dp[i] en la opción de llevarlo? Porque cada objeto se puede usar una sola vez: si lo llevo, el resto de la mochila se llena solo con los anteriores.

Mochila01.java
public static int mochila(int[] pesos, int[] valores, int capacidad) {
    int n = pesos.length;
    int[][] dp = new int[n + 1][capacidad + 1];   // fila 0 y columna 0 quedan en 0

    for (int i = 1; i <= n; i++) {
        for (int pesoActual = 0; pesoActual <= capacidad; pesoActual++) {
            if (pesos[i - 1] <= pesoActual) {
                dp[i][pesoActual] = Math.max(
                        dp[i - 1][pesoActual],
                        valores[i - 1] + dp[i - 1][pesoActual - pesos[i - 1]]);
            } else {
                dp[i][pesoActual] = dp[i - 1][pesoActual];
            }
        }
    }
    return dp[n][capacidad];
}

Ojo con los índices: la fila i corresponde al objeto i − 1 de los arreglos, porque la fila 0 es "sin objetos".

El error más común al hacer la tabla a mano

Cuando el objeto no entra (o no conviene), la celda copia la de arriba, no se pone 0. La fila i representa "los primeros i objetos", así que siempre puede hacer lo mismo que la fila anterior. Ninguna celda puede ser menor que la de arriba.

Reconstruir qué objetos se llevan: arrancás en dp[n][W] y subís fila por fila. Si dp[i][w] ≠ dp[i-1][w], el objeto i se llevó: lo anotás y restás su peso a w. Si son iguales, no se llevó.

Complejidad: O(n · W) en tiempo y memoria. Ojo: depende del valor de W, no de cuántos objetos hay. Con W = mil millones la tabla no entra en memoria. Por eso se dice que es pseudo-polinomial.

Mínima cantidad de monedas

Es el caso donde Greedy fallaba con {1, 3, 4}.

  1. Estado: dp[m] = mínima cantidad de monedas para pagar exactamente m.
  2. Última decisión: la última moneda fue alguna c. Antes de ponerla tenía que pagar m − c de la mejor forma: dp[m] = min sobre cada moneda c ≤ m de (dp[m - c] + 1).
  3. Base: dp[0] = 0.
MonedasPD.java
public static int monedasPD(int[] monedas, int monto) {
    int INF = Integer.MAX_VALUE / 2;    // evita overflow al sumar 1
    int[] dp = new int[monto + 1];
    Arrays.fill(dp, INF);
    dp[0] = 0;

    for (int m = 1; m <= monto; m++) {
        for (int c : monedas) {
            if (c <= m && dp[m - c] + 1 < dp[m]) {
                dp[m] = dp[m - c] + 1;
            }
        }
    }
    return dp[monto];   // si quedó INF, no se puede pagar
}

Cantidad de formas de pagar un monto

Otra pregunta, otra recurrencia. dp[m] = cuántas formas distintas hay de pagar m. Para no contar "2+1" y "1+2" como distintas, se procesan las monedas de a una en el bucle de afuera: primero las formas usando solo la primera moneda, después agregando la segunda, etc.

FormasMonedas.java
public static int formas(int[] monedas, int monto) {
    int[] dp = new int[monto + 1];
    dp[0] = 1;                          // una forma de pagar 0: no dar nada
    for (int c : monedas) {             // monedas afuera: combinaciones, no órdenes
        for (int m = c; m <= monto; m++) {
            dp[m] += dp[m - c];
        }
    }
    return dp[monto];
}

AvanzadoSubsecuencia común más larga (LCS)

En la vida real

Cuando Git o un comparador de archivos te muestra qué líneas cambiaron entre dos versiones, por debajo está buscando lo más largo que las dos tienen en común y en el mismo orden. Lo mismo se usa para comparar cadenas de ADN o para el autocorrector.

Una subsecuencia se obtiene borrando letras sin cambiar el orden de las que quedan ("ACE" es subsecuencia de "ABCDE"; no tiene que ser contigua). Dadas dos cadenas X e Y, buscamos la subsecuencia común más larga.

  1. Estado: dp[i][j] = largo de la LCS entre los primeros i caracteres de X y los primeros j de Y.
  2. Última decisión (mirando el último carácter de cada prefijo):
    • Si X[i] == Y[j]: ese carácter entra en la LCS. dp[i][j] = dp[i-1][j-1] + 1 (diagonal + 1).
    • Si son distintos: alguno de los dos sobra. dp[i][j] = max(dp[i-1][j], dp[i][j-1]) (el mejor entre arriba e izquierda).
  3. Base: fila 0 y columna 0 en 0 (con una cadena vacía no hay nada en común).
LCS.java
public static int lcs(String x, String y) {
    int[][] dp = new int[x.length() + 1][y.length() + 1];
    for (int i = 1; i <= x.length(); i++) {
        for (int j = 1; j <= y.length(); j++) {
            if (x.charAt(i - 1) == y.charAt(j - 1)) {
                dp[i][j] = dp[i - 1][j - 1] + 1;
            } else {
                dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]);
            }
        }
    }
    return dp[x.length()][y.length()];
}

  • Mochila: la fila i usa pesos[i-1] (desfase de índices).
  • Monedas: "mínima cantidad" usa min; "cantidad de formas" usa + y las monedas en el bucle de afuera.
  • PD no es "recursión con un arreglo": la clave son los subproblemas superpuestos. Si no se repiten, guardar no ahorra nada.

Unidad 6 · Tema 2.4 del programa

Backtracking

"Pruebo una posibilidad; si no funciona, vuelvo atrás y pruebo otra." Es una búsqueda sistemática: construís la solución de a una decisión por vez y, cuando una decisión no lleva a nada, la deshacés y probás la siguiente.

RutaLa idea→Permutaciones→Subconjuntos→Poda→N-Reinas→Escribirlo de cero→Para el parcial

BásicoLa idea

En la vida real

Estás en un laberinto. En cada bifurcación elegís un camino y seguís. Si llegás a una pared, volvés hasta la última bifurcación y probás el camino que no habías probado. Si ya probaste todos los de esa bifurcación, volvés a la anterior. Nunca recorrés dos veces el mismo camino y, si hay salida, la encontrás. Eso es backtracking.

Y si en una bifurcación ves un cartel de "sin salida", ni entrás: eso es podar.

El patrón siempre es el mismo: Elegir → Explorar → Deshacer.

Las decisiones forman un árbol de estados: la raíz es "no decidí nada", cada nivel es una decisión y cada hoja es una solución completa (o un callejón sin salida). Backtracking recorre ese árbol en profundidad. El deshacer es lo que deja el estado exactamente como estaba antes de entrar a una rama, listo para probar la siguiente.

Esquema general
void backtracking(Estado estado) {
    if (esSolucion(estado)) {
        procesarSolucion(estado);
        return;
    }
    for (Opcion opcion : opciones(estado)) {
        if (esValida(estado, opcion)) {     // poda
            // 1. ELEGIR
            elegir(estado, opcion);
            // 2. EXPLORAR
            backtracking(estado);
            // 3. DESHACER
            deshacer(estado, opcion);
        }
    }
}

BásicoPermutaciones

En la vida real

Tres amigos (1, 2 y 3) se ponen en fila para una foto y querés probar todos los órdenes. Elegís quién va primero; con los que quedan, quién va segundo; el último va solo. Después de sacar la foto 1-2-3, "deshacés" al 3 y al 2, y probás poner al 3 segundo: 1-3-2. Y así.

Permutaciones.java
void permutar(List<Integer> actual, List<Integer> restantes) {
    if (restantes.isEmpty()) {
        System.out.println(actual);
        return;
    }
    for (int i = 0; i < restantes.size(); i++) {
        int elemento = restantes.get(i);

        // Elegir
        actual.add(elemento);
        restantes.remove(i);

        // Explorar
        permutar(actual, restantes);

        // Deshacer
        restantes.add(i, elemento);
        actual.remove(actual.size() - 1);
    }
}

IntermedioSubconjuntos

En la vida real

Armás una pizza con 3 ingredientes posibles (jamón, morrón, aceitunas). Para cada uno decidís: va o no va. Dos opciones por ingrediente, tres ingredientes: 2 × 2 × 2 = 8 pizzas posibles (incluida la de solo muzzarella).

Subconjuntos.java
void subconjuntos(int[] v, int i, List<Integer> actual) {
    if (i == v.length) {
        System.out.println(actual);
        return;
    }
    // incluyo v[i]
    actual.add(v[i]);
    subconjuntos(v, i + 1, actual);
    actual.remove(actual.size() - 1);    // deshago

    // no incluyo v[i]
    subconjuntos(v, i + 1, actual);
}

Complejidad: O(2ⁿ). La complejidad de backtracking depende del problema: permutaciones es factorial, subconjuntos es exponencial.

IntermedioPoda (pruning)

Si en algún momento sabés que una elección ya no puede llevar a una solución válida, no seguís explorando esa rama: "desde acá no hay solución, no sigo". Eso es lo que separa a Backtracking de la fuerza bruta, que genera todas las combinaciones completas y recién al final se fija cuáles sirven.

En la vida real

Tenés $10 y querés comprar productos que sumen justo $10. Si ya cargaste $9 en el changuito y el próximo producto sale $5, no tiene sentido seguir probando con ese producto ni con los más caros: te pasás seguro. Podás esa rama entera sin mirarla.

Suma de subconjuntos

Encontrar los subconjuntos de {2, 3, 5, 7} que suman exactamente 10. Con el arreglo ordenado, si sumar v[j] ya se pasa, sumar cualquiera de los siguientes (más grandes) también: se corta el for entero.

SumaSubconjuntos.java
// v ordenado de menor a mayor
void sumaSubconjuntos(int[] v, int i, int suma, int objetivo, List<Integer> actual) {
    if (suma == objetivo) {
        System.out.println(actual);
        return;
    }
    for (int j = i; j < v.length; j++) {
        if (suma + v[j] > objetivo) {
            break;                       // poda: los siguientes son más grandes
        }
        actual.add(v[j]);
        sumaSubconjuntos(v, j + 1, suma + v[j], objetivo, actual);
        actual.remove(actual.size() - 1);
    }
}

AvanzadoN-Reinas

Colocar n reinas en un tablero de n × n sin que se ataquen (ni misma fila, ni misma columna, ni misma diagonal). Se pone una reina por fila. En cada fila se prueba cada columna; si la casilla está atacada por una reina anterior, se poda.

NReinas.java
// reinas[f] = columna de la reina de la fila f
boolean esSeguro(int[] reinas, int fila, int col) {
    for (int f = 0; f < fila; f++) {
        int c = reinas[f];
        if (c == col || Math.abs(c - col) == fila - f) {
            return false;    // misma columna o misma diagonal
        }
    }
    return true;
}

void nReinas(int[] reinas, int fila) {
    int n = reinas.length;
    if (fila == n) {
        System.out.println(Arrays.toString(reinas));
        return;
    }
    for (int col = 0; col < n; col++) {
        if (esSeguro(reinas, fila, col)) {
            reinas[fila] = col;           // elegir
            nReinas(reinas, fila + 1);    // explorar
            reinas[fila] = -1;            // deshacer
        }
    }
}

Dos reinas están en la misma diagonal si la distancia entre columnas es igual a la distancia entre filas: |c1 − c2| == |f1 − f2|. No hace falta chequear filas porque se pone una por fila.

AvanzadoCómo escribir un backtracking desde cero

Contestá estas preguntas en orden. Cada respuesta es una parte del método:

  1. ¿Qué es una solución parcial? Eso son los parámetros: la lista que voy armando, el índice por el que voy, la suma acumulada…
  2. ¿Cuándo está completa? Ese es el caso base: imprimo/guardo y return.
  3. ¿Qué opciones tengo en este paso? Ese es el for (o las dos llamadas, si es "incluyo / no incluyo").
  4. ¿Cuándo una opción no puede servir? Esa es la poda: un if antes de elegir, o un break.
  5. Elegir, explorar, deshacer: modifico el estado, llamo con el paso siguiente, y dejo el estado como estaba.

Aplicado: combinaciones de k elementos

Todas las formas de elegir k elementos de {1, …, n} sin importar el orden (elegir 2 sabores de helado de 4). (1) Parcial = lista elegida y desde qué número sigo. (2) Completa con k elementos. (3) Opciones = números desde desde hasta n, siempre hacia adelante para no repetir [2,1] si ya tuve [1,2]. (4) Poda = si no quedan suficientes números para completar.

Combinaciones.java
void combinaciones(int n, int k, int desde, List<Integer> actual) {
    if (actual.size() == k) {
        System.out.println(actual);
        return;
    }
    for (int x = desde; x <= n; x++) {
        int faltan = k - actual.size();
        if (n - x + 1 < faltan) {
            break;                            // poda: no alcanzan los números
        }
        actual.add(x);                        // elegir
        combinaciones(n, k, x + 1, actual);   // explorar
        actual.remove(actual.size() - 1);     // deshacer
    }
}

Poda por cota (ramificación y poda)

En problemas de optimización (maximizar o minimizar) se puede podar más fuerte: si ya encontraste una solución con valor mejor, y la rama actual, aunque le salga todo perfecto, no puede superarlo, no vale la pena seguir. Ejemplo con la Mochila 0/1: la cota optimista es "lo que llevo + el valor de todos los objetos que quedan".

MochilaBacktracking.java
int mejor = 0;

// restante = suma de valores de los objetos i..n-1
void mochila(int[] p, int[] v, int i, int peso, int valor, int restante, int W) {
    if (valor > mejor) {
        mejor = valor;
    }
    if (i == p.length) {
        return;
    }
    if (valor + restante <= mejor) {
        return;                    // poda por cota: ni llevando todo supero al mejor
    }
    int resto = restante - v[i];
    if (peso + p[i] <= W) {        // poda por factibilidad: tiene que entrar
        mochila(p, v, i + 1, peso + p[i], valor + v[i], resto, W);   // lo llevo
    }
    mochila(p, v, i + 1, peso, valor, resto, W);                     // no lo llevo
}

Con capacidad 50 y objetos (10, 60), (20, 100), (30, 120) encuentra 220 visitando 12 nodos en vez de los 15 del árbol completo. Sigue siendo O(2n) en el peor caso; la poda mejora la práctica, no la cota teórica. Para la 0/1, la PD (O(n · W)) suele ser mejor.

Grafos y recorridos (BFS y DFS)

Un grafo modela cosas conectadas: ciudades y rutas, personas y amistades, materias y correlativas. Recorrer un grafo es visitar todos sus vértices de forma ordenada, y las dos maneras de hacerlo (a lo ancho y en profundidad) son la base de casi todos los algoritmos de grafos.

BásicoQué es un grafo

Un grafo G = (V, E) es un conjunto de vértices (nodos) y un conjunto de aristas que unen pares de vértices. V es la cantidad de vértices y E la de aristas (de edges).

En la vida real
  • El subte: las estaciones son vértices y los tramos de vía son aristas.

IntermedioBFS: recorrido a lo ancho

En la vida real

Tirás una piedra en un lago: las ondas se expanden en círculos, primero lo que está a distancia 1, después a distancia 2, etc. O en LinkedIn: tus contactos son de "1er grado", los contactos de ellos de "2do grado", y así. BFS (Breadth-First Search) recorre el grafo exactamente así: por niveles de distancia desde el origen.

Para respetar los niveles usa una cola (FIFO): los vecinos que descubrís van al final de la fila, así que primero se atiende a todos los del nivel actual antes de pasar al siguiente.

  1. Marcar el origen como visitado y meterlo en la cola.
  2. Mientras la cola no esté vacía: sacar el primero (u) y procesarlo.
  3. Por cada vecino de u que no esté visitado: marcarlo como visitado, anotar su nivel (nivel[u] + 1) y meterlo en la cola.
BFS.java
public static List<Integer> bfs(List<List<Integer>> grafo, int origen) {
    boolean[] visitado = new boolean[grafo.size()];
    int[] nivel = new int[grafo.size()];
    Queue<Integer> cola = new LinkedList<>();
    List<Integer> orden = new ArrayList<>();

    visitado[origen] = true;
    nivel[origen] = 0;
    cola.add(origen);

    while (!cola.isEmpty()) {
        int u = cola.poll();
        orden.add(u);
        for (int v : grafo.get(u)) {
            if (!visitado[v]) {
                visitado[v] = true;       // se marca al encolar, no al sacar
                nivel[v] = nivel[u] + 1;
                cola.add(v);
            }
        }
    }
    return orden;
}

El nivel de cada vértice es la cantidad mínima de aristas para llegar desde A. Por eso BFS resuelve el camino mínimo en grafos sin pesos (todas las aristas valen 1).

IntermedioDFS: recorrido en profundidad

En la vida real

Volvemos al laberinto: entrás por un pasillo y seguís lo más profundo que puedas. Cuando llegás a un lugar sin salidas nuevas, volvés al último cruce que tenía un pasillo sin explorar. DFS (Depth-First Search) es eso, y es backtracking sobre un grafo.

Usa una pila (LIFO). La forma más natural es la recursión, que usa la pila de llamadas: visito u y, por cada vecino no visitado, me tiro de cabeza a visitarlo antes de mirar al siguiente vecino.

DFS.java
// recursivo
public static void dfs(List<List<Integer>> grafo, int u,
                       boolean[] visitado, List<Integer> orden) {
    visitado[u] = true;
    orden.add(u);
    for (int v : grafo.get(u)) {
        if (!visitado[v]) {
            dfs(grafo, v, visitado, orden);
        }
    }
}

// iterativo con pila explícita
public static List<Integer> dfsIterativo(List<List<Integer>> grafo, int origen) {
    boolean[] visitado = new boolean[grafo.size()];
    Deque<Integer> pila = new ArrayDeque<>();
    List<Integer> orden = new ArrayList<>();
    pila.push(origen);
    while (!pila.isEmpty()) {
        int u = pila.pop();
        if (visitado[u]) {
            continue;
        }
        visitado[u] = true;
        orden.add(u);
        List<Integer> vecinos = grafo.get(u);
        for (int i = vecinos.size() - 1; i >= 0; i--) {   // al revés para respetar el orden
            if (!visitado[vecinos.get(i)]) {
                pila.push(vecinos.get(i));
            }
        }
    }
    return orden;
}

Componentes conexas

Un recorrido desde un vértice visita exactamente su componente. Para contar componentes (grupos de amigos que no se conocen entre sí, islas en un mapa), recorrés desde cada vértice que todavía no fue visitado y contás cuántas veces arrancaste.

Componentes.java
public static int contarComponentes(List<List<Integer>> grafo) {
    boolean[] visitado = new boolean[grafo.size()];
    int componentes = 0;
    for (int i = 0; i < grafo.size(); i++) {
        if (!visitado[i]) {
            componentes++;
            dfs(grafo, i, visitado, new ArrayList<>());   // marca toda su componente
        }
    }
    return componentes;
}

boolean hayCiclo(List<List<Integer>> grafo, int u, int padre, boolean[] visitado) {

        if (!visitado[v]) {
            if (hayCiclo(grafo, v, u, visitado)) {
                return true;
            }
        } else if (v != padre) {

Orden topológico: en qué orden cursar las materias

En la vida real

Querés armar un plan para cursar todas las materias respetando las correlativas. Un orden topológico es una lista de los vértices de un DAG donde cada flecha va de uno anterior a uno posterior: nunca cursás algo antes de su correlativa.

Matemática Discreta (MD) ──────────────┐
Prog I (P1) → Prog II (P2) → AED ←──────┘   (AED necesita P2 y MD)
                        │        │
                        ↓        ↓
                  Bases de Datos  Prog III
                        │        │
                        └→ Seminario ←┘     (Seminario necesita BD y P3)

Algoritmo de Kahn (con una cola, como BFS): llevás la cuenta de cuántas correlativas le faltan a cada materia (su grado de entrada). Las que no necesitan nada se pueden cursar ya: van a la cola. Cada vez que "cursás" una, le restás 1 a las que dependían de ella; si alguna llega a 0, se habilita.

OrdenTopologico.java
public static List<Integer> ordenTopologico(List<List<Integer>> grafo) {
    int n = grafo.size();
    int[] gradoEntrada = new int[n];
    for (int u = 0; u < n; u++) {
        for (int v : grafo.get(u)) {
            gradoEntrada[v]++;
        }
    }
    Queue<Integer> cola = new LinkedList<>();
    for (int i = 0; i < n; i++) {
        if (gradoEntrada[i] == 0) {
            cola.add(i);                 // no necesita nada: se puede cursar
        }
    }
    List<Integer> orden = new ArrayList<>();
    while (!cola.isEmpty()) {
        int u = cola.poll();
        orden.add(u);
        for (int v : grafo.get(u)) {
            gradoEntrada[v]--;           // u ya está aprobada
            if (gradoEntrada[v] == 0) {
                cola.add(v);
            }
        }
    }
    // si orden.size() < n, había un ciclo: no existe orden topológico
    return orden;
}

7.7

¿Por qué BFS cuesta O(V + E) con lista de adyacencia y O(V2) con matriz?

Ver resolución

Cada vértice entra y sale de la cola una vez (O(V)). Además, por cada vértice se recorren sus vecinos. Con lista, eso es la suma de todos los grados, que es 2E: total O(V + E). Con matriz, para encontrar los vecinos hay que recorrer la fila entera (V casillas) por cada vértice: V · V. En un grafo denso (E ≈ V2) dan lo mismo; en uno disperso, la lista gana por mucho.

BásicoLa idea que comparten: relajar una arista

Todos llevan un arreglo dist[] con la mejor distancia conocida hasta cada vértice. Al principio dist[origen] = 0 y el resto ∞, porque todavía no sabemos cómo llegar. Cualquier camino que aparezca va a ser mejor que "no tengo camino".

Relajar la arista (u, v) es preguntarse: ¿llego a v más barato si paso por u?

si   dist[u] + peso(u, v) < dist[v]
dist[v] = dist[u] + peso(u, v)    // encontré un camino estrictamente mejor
prev[v] = u                       // y vengo desde u
En la vida real

Ibas a ir al centro en taxi por $5.000. Un amigo te dice "tomá el tren hasta Retiro ($800) y de ahí un colectivo ($600)". Comparás: $1.400 < $5.000, así que actualizás tu mejor opción y anotás que llegás "vía Retiro". Eso es relajar. Lo que cambia entre algoritmos es en qué orden se relajan las aristas.

prev[v] guarda desde qué vértice se llega a v en el mejor camino. Siguiéndolo hacia atrás se reconstruye el recorrido.

IntermedioDijkstra

En la vida real

Imaginá que se prende fuego un pastizal en el origen y el fuego avanza por las calles a velocidad constante. El primer momento en que el fuego llega a una esquina es la distancia mínima hasta ahí: ya no puede llegar antes por otro lado. Dijkstra simula eso: siempre avanza hacia el vértice más cercano que todavía no alcanzó, y en ese momento su distancia queda fija.

  1. dist[origen] = 0, el resto ∞. Ninguno fijado.
  2. Elegir el vértice no fijado con menor dist. Esa distancia ya es definitiva: lo fijo.
  3. Relajar todas sus aristas.
  4. Repetir hasta fijar todos.

Elegir siempre el más cercano y no volver a tocarlo es una decisión Greedy.

Dijkstra.java
class Arista {
    int origen, destino, peso;
    Arista(int origen, int destino, int peso) {
        this.origen = origen; this.destino = destino; this.peso = peso;
    }
}

class Nodo {
    int vertice, distancia;
    Nodo(int vertice, int distancia) {
        this.vertice = vertice; this.distancia = distancia;
    }
}

public static int[] dijkstra(List<List<Arista>> grafo, int inicio, int[] prev) {
    int n = grafo.size();
    int[] distancia = new int[n];
    boolean[] visitado = new boolean[n];

    Arrays.fill(distancia, Integer.MAX_VALUE);   // "infinito"
    Arrays.fill(prev, -1);
    distancia[inicio] = 0;

    PriorityQueue<Nodo> cola = new PriorityQueue<>(
            Comparator.comparingInt(a -> a.distancia));
    cola.add(new Nodo(inicio, 0));

    while (!cola.isEmpty()) {
        Nodo actual = cola.poll();
        int u = actual.vertice;

        if (visitado[u]) {
            continue;          // entrada vieja de la cola
        }
        visitado[u] = true;    // su distancia ya es definitiva

        for (Arista vecino : grafo.get(u)) {
            int v = vecino.destino;
            int peso = vecino.peso;

            // RELAJACIÓN
            if (distancia[u] != Integer.MAX_VALUE
                    && distancia[u] + peso < distancia[v]) {
                distancia[v] = distancia[u] + peso;
                prev[v] = u;
                cola.add(new Nodo(v, distancia[v]));
            }
        }
    }
    return distancia;
}

// reconstruir el camino hasta destino
List<Integer> camino(int[] prev, int destino) {
    List<Integer> c = new ArrayList<>();
    for (int v = destino; v != -1; v = prev[v]) {
        c.add(0, v);       // se arma de atrás para adelante
    }
    return c;
}
  • La cola de prioridad es la guardia del hospital: siempre sale el de menor distancia, sin recorrer todo el arreglo.
  • distancia[u] != Integer.MAX_VALUE evita que MAX_VALUE + peso desborde a negativo.
  • Un vértice puede entrar varias veces a la cola (cada vez que mejora). Las entradas viejas se ignoran con el if (visitado[u]) continue.
  • Complejidad: O((V + E) log V). Sin cola de prioridad (buscando el mínimo con un for) es O(V2).
Dijkstradist[], fijados y relajaciones

AvanzadoPor qué Dijkstra no funciona con pesos negativos

Dijkstra asume que cuando fija un vértice, ningún camino que todavía no exploró puede ser más corto. Con pesos ≥ 0 es cierto: cualquier camino nuevo pasa por vértices que ya están más lejos, y agregarle aristas solo lo alarga (en la analogía, el fuego no puede llegar "más rápido" dando la vuelta). Con una arista negativa, un camino largo puede terminar siendo más corto.

dirigido:  A→B 4,  A→C 5,  C→B -3,  B→D 2,  C→D 6

Dijkstra desde A:
  fija A (0):  B = 4, C = 5
  fija B (4):  relaja B→D: D = 4 + 2 = 6     ← B se fija con 4 y D se calcula con ese 4
  fija C (5):  relaja C→B: 5 - 3 = 2 < 4 → B = 2 … pero B ya estaba fijado:
               nunca se vuelven a relajar sus aristas, así que D no se entera
  fija D (6)
  resultado: B = 2, D = 6

Real:  A→C→B = 2  y  A→C→B→D = 4

Con el código de arriba, B termina bien (el if de la relajación igual lo actualiza), pero D queda mal: se calculó con el B "viejo" y, como B ya estaba fijado, la mejora no se propaga. Según cómo esté implementado, incluso B puede quedar en 4. En cualquier caso, la garantía de Dijkstra se rompe. Para esto existe Bellman-Ford.

AvanzadoBellman-Ford

En la vida real

Un grupo de amigos en distintas ciudades quiere saber cuánto les sale llegar a Buenos Aires. Cada ronda, todos le preguntan a sus vecinos "¿a vos cuánto te sale?" y, si pasando por un vecino les sale más barato, actualizan su número. No eligen a nadie en especial: todos revisan todo, ronda tras ronda. Después de suficientes rondas, nadie puede mejorar más.

En vez de elegir con cuidado qué vértice procesar (como Dijkstra), relaja todas las aristas, y lo repite V − 1 veces.

¿Por qué V − 1 rondas? Un camino mínimo sin ciclos pasa por como mucho V vértices, o sea V − 1 aristas. Después de la ronda 1 están bien todos los caminos mínimos de 1 arista; después de la ronda 2, los de hasta 2 aristas; y así. A la ronda V − 1 están todos.

BellmanFord.java
// devuelve false si hay un ciclo negativo alcanzable
public static boolean bellmanFord(List<Arista> aristas, int n, int origen, int[] dist) {
    int INF = Integer.MAX_VALUE;
    Arrays.fill(dist, INF);
    dist[origen] = 0;

    for (int ronda = 1; ronda <= n - 1; ronda++) {
        boolean huboCambio = false;
        for (Arista a : aristas) {
            if (dist[a.origen] != INF && dist[a.origen] + a.peso < dist[a.destino]) {
                dist[a.destino] = dist[a.origen] + a.peso;
                huboCambio = true;
            }
        }
        if (!huboCambio) {
            break;               // ya no mejora nada: terminé antes
        }
    }
    // ronda extra: si algo todavía mejora, hay un ciclo negativo
    for (Arista a : aristas) {
        if (dist[a.origen] != INF && dist[a.origen] + a.peso < dist[a.destino]) {
            return false;
        }
    }
    return true;
}

Ciclos negativos

Si hay un ciclo cuya suma es negativa, dar otra vuelta siempre abarata: no existe camino mínimo (sería −∞). Ejemplo: B→C −2 y C→B 1 forman un ciclo de costo −1. Bellman-Ford lo detecta con la ronda extra: si después de V − 1 rondas todavía se puede mejorar algo, es que hay un ciclo negativo.

Complejidad: V − 1 rondas × E aristas = O(V · E). Más lento que Dijkstra, por eso solo se usa cuando hay negativos.

AvanzadoFloyd-Warshall (todos contra todos)

En la vida real

Armás la tabla de precios de vuelos entre todas las ciudades. Arrancás solo con los vuelos directos. Después te preguntás: "¿y si permito hacer escala en Córdoba?". Para cada par de ciudades, comparás el directo con "ir a Córdoba + de Córdoba al destino" y te quedás con el más barato. Después permitís escala en Mendoza, después en Salta… Cuando permitiste escala en todas, la tabla tiene el mejor precio entre cualquier par.

Es Programación Dinámica sobre una matriz dist[i][j]. En la vuelta k se permite usar el vértice k como intermedio:

dist[i][j] = min( dist[i][j],  dist[i][k] + dist[k][j] )¿me conviene pasar por k?
FloydWarshall.java
// dist empieza con los pesos directos, 0 en la diagonal e INF donde no hay arista
public static void floyd(int[][] dist) {
    int n = dist.length;
    int INF = Integer.MAX_VALUE;
    for (int k = 0; k < n; k++) {              // intermedio permitido (va AFUERA)
        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                if (dist[i][k] != INF && dist[k][j] != INF
                        && dist[i][k] + dist[k][j] < dist[i][j]) {
                    dist[i][j] = dist[i][k] + dist[k][j];
                }
            }
        }
    }
}

Árboles de recubrimiento mínimo

Dado un grafo conexo, no dirigido y ponderado, encontrar la forma más barata de conectar todos los vértices. Kruskal y Prim lo resuelven con dos estrategias Greedy distintas.

BásicoLa idea

En la vida real

Una empresa tiene que llevar fibra óptica a 6 barrios. Tiene un presupuesto de cuánto cuesta cada tendido posible entre pares de barrios. No le importa por dónde pase la señal, solo que todos queden conectados (directa o indirectamente) y gastar lo menos posible. Nunca va a tender un cable que cierre un círculo, porque sería plata tirada: esos barrios ya estaban conectados.

Un árbol de recubrimiento (o de expansión, spanning tree) es un subconjunto de aristas que conecta todos los vértices sin formar ciclos. Como es un árbol, tiene exactamente V − 1 aristas. El mínimo (MST, Minimum Spanning Tree) es el de menor suma de pesos.

Kruskal

"Voy agarrando los tendidos más baratos de toda la lista, salteando los que cerrarían un círculo."

¿Cuál es la arista más barata de todo el grafo que todavía me sirve?

Prim

"Arranco en un barrio y voy sumando el tendido más barato que conecte mi red con un barrio que todavía no está."

Desde mi red actual, ¿cuál es la arista más barata para crecer?

IntermedioKruskal

  1. Ordenar todas las aristas de menor a mayor peso.
  2. Recorrerlas en ese orden. Si une dos vértices que todavía no están conectados, se agrega. Si ya estaban conectados (por otro camino), formaría un ciclo: se descarta.
  3. Cortar cuando se tienen V − 1 aristas.

Durante Kruskal puede haber varios "pedazos" sueltos que después se unen: no crece como un solo árbol. La pregunta clave es "¿estos dos ya están en el mismo grupo?", y para responderla rápido está Union-Find.

IntermedioUnion-Find (conjuntos disjuntos)

En la vida real

Pensá en equipos de un torneo, cada uno con un capitán. Para saber si dos jugadores están en el mismo equipo, cada uno le pregunta a su "referente", que le pregunta al suyo, hasta llegar al capitán. Si los dos llegan al mismo capitán, son del mismo equipo. Para fusionar dos equipos, alcanza con que un capitán pase a responder al otro.

  • padre[x] = el "referente" de x. El capitán (la raíz) es su propio padre.
  • find(x): sube de padre en padre hasta la raíz. Dos vértices están en el mismo grupo si tienen la misma raíz.
  • union(a, b): une los dos grupos haciendo que la raíz de uno apunte a la raíz del otro.
UnionFind.java
class UnionFind {
    int[] padre;

    public UnionFind(int n) {
        padre = new int[n];
        for (int i = 0; i < n; i++) {
            padre[i] = i;          // cada uno es su propio grupo
        }
    }

    public int find(int x) {
        if (padre[x] != x) {
            padre[x] = find(padre[x]);   // compresión de camino
        }
        return padre[x];
    }

    public void union(int a, int b) {
        int raizA = find(a);
        int raizB = find(b);
        padre[raizA] = raizB;
    }
}

La línea padre[x] = find(padre[x]) es la compresión de camino: mientras busca la raíz, deja a todos los del camino apuntando directo al capitán. Las próximas preguntas son casi instantáneas.

AvanzadoEl código de Kruskal

Kruskal.java
public static List<Arista> kruskal(List<Arista> aristas, int vertices) {
    // 1. Ordenamos por peso
    aristas.sort(Comparator.comparingInt(a -> a.peso));

    List<Arista> resultado = new ArrayList<>();
    UnionFind uf = new UnionFind(vertices);

    // 2. Revisamos las aristas
    for (Arista arista : aristas) {
        int raizOrigen = uf.find(arista.origen);
        int raizDestino = uf.find(arista.destino);

        // Si pertenecen a conjuntos distintos, no forma ciclo
        if (raizOrigen != raizDestino) {
            resultado.add(arista);
            uf.union(arista.origen, arista.destino);
        }

        // Un MST tiene V - 1 aristas
        if (resultado.size() == vertices - 1) {
            break;
        }
    }
    return resultado;
}

Complejidad: ordenar las aristas cuesta O(E log E) y las operaciones de Union-Find son casi constantes. Total O(E log E) (igual a O(E log V)).

IntermedioPrim

  1. Arrancar desde un vértice cualquiera. Marcarlo como visitado.
  2. Meter en una cola de prioridad todas las aristas que salen de él.
  3. Sacar la arista más barata. Si su destino ya está en el árbol, se ignora (formaría ciclo). Si no, se agrega, se marca el destino y se encolan sus aristas hacia vértices no visitados.
  4. Repetir hasta que la cola quede vacía (o se visiten todos).

Prim.java
public static int prim(List<List<Arista>> grafo, int inicio) {
    int vertices = grafo.size();
    boolean[] visitado = new boolean[vertices];

    PriorityQueue<Arista> cola = new PriorityQueue<>(
            Comparator.comparingInt(a -> a.peso));

    // arista ficticia de costo 0 para entrar al vértice inicial
    cola.add(new Arista(-1, inicio, 0));
    int costoTotal = 0;

    while (!cola.isEmpty()) {
        Arista actual = cola.poll();

        // Si ya está en el árbol, se descarta
        if (visitado[actual.destino]) {
            continue;
        }

        // Lo agregamos
        visitado[actual.destino] = true;
        costoTotal += actual.peso;

        // Agregamos las conexiones hacia vértices nuevos
        for (Arista vecino : grafo.get(actual.destino)) {
            if (!visitado[vecino.destino]) {
                cola.add(vecino);
            }
        }
    }
    return costoTotal;
}

Complejidad: cada arista entra y sale de la cola como mucho una vez, a O(log E) cada operación: O(E log V).

ParcialPor qué funcionan (y trampas)

La propiedad del corte

Si partís los vértices en dos grupos cualesquiera (un "corte"), la arista más barata que cruza de un grupo al otro pertenece a algún MST. Razón: cualquier árbol tiene que cruzar ese corte con alguna arista; si un árbol usara una más cara, cambiándola por la más barata seguís conectando todo y gastás menos (es el argumento de intercambio de Greedy).

  • Prim aplica esto directamente: el corte es "mi árbol" vs "el resto", y agrega la arista más barata que cruza.
  • Kruskal también: cuando agrega una arista que une dos pedazos, es la más barata que cruza el corte entre uno de esos pedazos y el resto (todas las más baratas ya se procesaron).
Trampas típicas
  • El MST no da el camino más corto entre dos vértices: minimiza el total, no cada camino (ver Dijkstra vs Prim).
  • Descartar una arista en Kruskal "porque es cara" no es la razón: se descarta porque forma ciclo.
  • En el Union-Find a mano, acordate de la compresión de camino al hacer find.
  • Kruskal y Prim funcionan con pesos negativos (Dijkstra no).

10.2

Un compañero dice: "PD y Divide y Conquista son lo mismo, los dos parten el problema en subproblemas". ¿Qué le contestás?

Ver resolución

Que los dos parten el problema, pero la diferencia está en los subproblemas. En D&C son independientes (las dos mitades de MergeSort no comparten nada), así que no hay nada que reusar. En PD se superponen: el mismo subproblema aparece muchas veces (fib(3) dentro de fib(5)), y PD lo calcula una sola vez. Si aplicás D&C a un problema con subproblemas superpuestos, te queda exponencial.

10.3

¿Por qué Greedy suele ser más rápido que PD, y por qué no se usa siempre?

Ver resolución

Greedy toma una decisión por paso y no la revisa: un sort y una pasada, O(n log n). PD considera todas las opciones de cada subproblema y llena una tabla entera. Pero Greedy solo da el óptimo cuando el problema cumple la propiedad de elección greedy; si no (monedas {1, 3, 4}, mochila 0/1), da una solución factible pero peor.

10.4

Dada esta función, escribí su recurrencia, resolvela, y proponé una versión más eficiente.

Java
int caminos(int f, int c) {
    if (f == 0 || c == 0) return 1;
    return caminos(f - 1, c) + caminos(f, c - 1);
}
Ver resolución

Con n = f + c: T(n) = 2T(n − 1) + 1 → O(2n), porque caminos(f-1, c-1) se calcula desde dos lados: subproblemas superpuestos. Solución con PD:

Java
int caminos(int f, int c) {
    int[][] dp = new int[f + 1][c + 1];
    for (int i = 0; i <= f; i++) {
        for (int j = 0; j <= c; j++) {
            if (i == 0 || j == 0) {
                dp[i][j] = 1;
            } else {
                dp[i][j] = dp[i - 1][j] + dp[i][j - 1];
            }
        }
    }
    return dp[f][c];
}

O(f · c)

10.5

Floyd-Warshall es PD y Dijkstra es Greedy, pero los dos calculan caminos mínimos. Explicá qué tiene cada uno de su técnica.

Ver resolución

Dijkstra es Greedy porque en cada paso elige el vértice más cercano no fijado y fija su distancia para siempre, sin revisarla (decisión local definitiva). Funciona gracias a que los pesos son ≥ 0.

Floyd es PD porque define un estado (dist[i][j] usando como intermedios solo los vértices hasta k), lo calcula a partir de subproblemas más chicos ya guardados (dist[i][k] y dist[k][j] de la vuelta anterior), y prueba las dos opciones (pasar o no por k) quedándose con la mejor.

Fórmulas

Teorema Maestro

T(n) = aT(n/b) + nd

  • d < logb a → nlogb a (ganan las hojas)
  • d = logb a → nd log n (empate)
  • d > logb a → nd (gana la raíz)

No aplica con T(n − 1): desenrollar.

Sumas y datos

  • 1 + 2 + … + n = n(n + 1)/2 → n2
  • 1 + 2 + 4 + … + n < 2n → n
  • n + n/2 + n/4 + … < 2n → n
  • i *= 2 o i /= 2 → log n
  • log2 3 ≈ 1,585 · log2 7 ≈ 2,807
  • Árbol con V vértices → V − 1 aristas

Trampas típicas

  • Lomuto: en el swap final se cambia v[i+1] con el pivote. Fijate qué número hay realmente en v[i+1].
  • Mochila 0/1 a mano: si no entra, copiá la de arriba. Ninguna celda es menor que la de arriba.
  • Escalera: dp[2] = 2. Para 5 escalones son 8.
  • Dijkstra: dist es acumulada desde el origen; la relajación pide estrictamente menor.
  • Actividades: la que termina antes, no la que dura menos ni la que empieza antes.
  • Greedy no sirve → mostralo con un contraejemplo concreto.
  • Pesos negativos: Dijkstra no; Bellman-Ford para caminos desde un origen, Floyd para todos los pares; Kruskal/Prim siguen andando para MST.
  • BFS: marcar visitado al encolar. Grafo no conexo: relanzar el recorrido desde cada no visitado.
  • Contá las llamadas recursivas que se ejecutan, no las que aparecen escritas (la binaria tiene dos en el código y ejecuta una).
  • Big O es una cota superior: n ∈ O(n2) es verdadero, aunque no ajustado.
